# Schedule

自然文の依頼からプロジェクトのスケジュールを組み立てる Claude Code 用スキル。
「11月中にリリースしたい」と伝えると、フェーズ・工程・マイルストン・タスクの階層に分解し、
稼働日と休日、依存関係、バッファを踏まえて日程を組む。

出来上がるのは**ガントチャート1枚の HTML ファイル**。外部のファイルを一切参照しないので、
そのまま誰かに送れば、受け取った人はブラウザで開くだけで同じものが見られる。サーバーもインターネット接続も要らない。

---

## 導入

**このリポジトリを Claude Code のスキルフォルダへ入れるだけで使える。** プラグインの登録・
インストールコマンドは不要。ターミナルを自分で操作する必要もない。Claude Code に次のように伝えれば、
**エージェントが `git clone` か zip 展開かをその場で判断して実行する。** 使う側が git の有無を
気にしたり、「git を入れてください」と言われたりすることは無い。

```
このリポジトリを ~/.claude/skills/schedule-gantt に入れて。
https://github.com/tamaki1982/schedule-skill
```

配置後、それより前から続いている会話では認識されないことがある。**新しく会話を始めれば使える。**

### エージェント向け: どちらの経路で入れるか

1. `git --version` などで git が使えるか確認する。
2. **使える場合**は `git clone https://github.com/tamaki1982/schedule-skill ~/.claude/skills/schedule-gantt`。
3. **使えない場合**は zip 経路に切り替える。
   `https://github.com/tamaki1982/schedule-skill/archive/refs/heads/main.zip` を取得して展開する。
   展開すると `schedule-skill-main/`（リポジトリ名 + ブランチ名）というフォルダ名になるので、
   その中身を `~/.claude/skills/schedule-gantt/` に置き直す（フォルダごと移動してリネームするか、
   中身だけをコピーする）。**利用者に途中経過を確認する必要は無い。**「入った」とだけ報告すればよい。

### 更新のしかた

| 導入経路 | 更新のしかた |
|---|---|
| `git clone` した場合 | `cd ~/.claude/skills/schedule-gantt && git pull` |
| zip で展開した場合 | zip を取得し直し、展開してできたフォルダの中身で `~/.claude/skills/schedule-gantt/` を丸ごと置き換える |

**どちらの経路でも、丸ごと置き換えて問題ない。** 生成物と自分用に書き換えた設定ファイルは
スキル本体とは別の場所（後述の「置き場」）にあり、スキル本体の更新・入れ替えの影響を受けない。

## 最初の1本を作る

1. 作りたいスケジュールをそのまま伝える。
2. 初回は、生成物と自分用の設定ファイルの置き場所（以下「置き場」）を確認される。候補が1つ
   提示されるので、そのままでよければ承認する。決めた場所は次回以降記録され、聞かれない。
3. 情報が足りない項目（着手時期・期限・分野・体制の規模など）は、**選択肢付きの質問でまとめて
   一度に**確認される。文章で何個も質問が並ぶことはない。選択肢に無い答えを書いてもよい。
4. 置き場の `output/` の中に HTML と JSON が対で出る。**HTML をブラウザで開けば完成。**

### 伝え方の例

```
社内ポータルにバーチャルオフィス機能を追加する。
11月中にリリースしたいので、逆算してスケジュールを作って
```

```
10/25 のユーザー向けイベントの準備スケジュールを作って。
告知は9月の頭から始めたい
```

```
受託案件を来週から着手して年内納品。工程表を引いて
```

### 一緒に伝えておくと精度が上がるもの

| 伝えること | 例 |
|---|---|
| いつまでに | 「11月中に」「年内に」「12/11 に公開」 |
| いつから | 「来週から」「年明けから」 |
| 体制 | 「実装は2名」「ひとりでやる」 |
| すでに決まっている日 | 「本番は 11/22（日）」 |
| 入れたい・要らない作業 | 「セキュリティ確認を入れて」「リハーサルは不要」 |

書かなくても、足りない項目は選択肢付きの質問で確認される。指定が無いものは推定して組み立てられ、
**何をどう推定したかは生成結果に残る。**

作った後に直したいときは、そのまま「実装を2週間後ろ倒しして」のように言えばよい
（詳しい実例は [`HOW-TO-REVISE.md`](HOW-TO-REVISE.md)）。

## 自分のやり方に合わせる

このツールの判断基準は、すべて**置き場にコピーされた** `definitions/` の中の Markdown ファイルに
書いてある。コードの中に基準は入っていない。**ここを書き換えるだけで、次に作るものが変わる。**
（このリポジトリ内の `definitions/` は配布時点の既定値であり、直接書き換えても効かない）

| やりたいこと | 開くファイル |
|---|---|
| 自分の組織のやり方に合わせたい（稼働日、目標日への向き合い方、作業の束ね方、呼び方） | `<置き場>/definitions/50-user-context.md` |
| 自分の分野を足したい（どんな作業が出てくるか、どれくらいかかるか、誰がやるか） | `<置き場>/definitions/90-how-to-add-preset.md` の手順で `<置き場>/definitions/presets/` にフォルダを足す |

まず `<置き場>/definitions/00-index.md` を読むと、どのファイルが何を決めているかが分かる。
書き換えも「見積もりを全体に1.2倍にして」のように AI に頼める。**書き換えても、すでに出来上がっている
資料は変わらない。** 次に作るものから効く。

エージェントに聞けば、上のどれも読んだうえで答える。
