# 体制と稼働

入力文で体制の指定がない場合に採用する前提。

## 1. 既定の体制

| 役割 id | 表示名 | 人数 | 実働係数 |
|---|---|---|---|
| `role-pm` | プロダクト管理 | 1 | 0.4 |
| `role-design` | デザイン | 1 | 0.5 |
| `role-backend` | バックエンド実装 | 1 | 0.8 |
| `role-frontend` | フロントエンド実装 | 1 | 0.8 |
| `role-qa` | 検証 | 1 | 0.6 |

実働係数は、1稼働日のうち当該案件に使える割合。
0.8 なら、5稼働日で投入できる工数は 4人日となる。会議・問い合わせ対応・他案件との掛け持ちを織り込んだ値。

所要日数は次式で算出する（式は共通側で決まっている）。

```
有効人数 = 1 + (人数 − 1) × 0.7
所要日数 = ceil( 工数(人日) / (有効人数 × 実働係数) )
```

2人目以降を 0.7 で数えるのは、分担とすり合わせに時間が取られるため。既定の1名では有効人数 1.0 になる。

`10-standard-tasks.md` 第1章で「増員が効かない」とされた標準作業（結合 / 動作テスト / 公開作業）には人数を掛けない。

**実働係数は役割に紐づく値であり、作業の種類には紐づかない。**

### 目標日に間に合わせるために増やす場合

`definitions/20-scheduling-rules.md` 第3章 Step 5 の2に当たる場合、次の範囲で増やしてよい。

| 項目 | 上限 |
|---|---|
| 1役割あたりの人数 | **既定の人数の3倍まで、かつ5名まで**（既定は各役割1名なので、実質3名まで。`50-user-context.md` 第2章で変えられる） |
| 増やしてよい役割 | 「増員が効く」標準作業を担う役割だけ |
| 実働係数 | **変えない。** 人を足すことと、1人あたりの集中度を上げることは別 |

増やした場合は、どの役割を何名にしたかを `meta.assumptions` と `risks` の両方に残し、報告でも伝える。

### 変更時の影響

- 人数を増やすと、同じ工数でも所要日数が短くなり、全体の期間が縮む。
- 実働係数を下げると全タスクの所要日数が伸びる。
  見積もりが常に楽観的すぎると感じたときは、標準日数ではなくここを下げるほうが影響が読みやすい。
- 役割を追加したら、`10-standard-tasks.md` の「既定の担当役割」からも参照できるようにする。

## 2. 同時並行の上限

| 項目 | 既定値 |
|---|---|
| 同時に走らせられる作業本数 | 3 |
| 1役割が同時に持てる作業本数 | 1 |

同じ役割のタスクを期間を重ねて配置しない。重ねる必要がある場合は、**直列に並べ直す。**
**人数を増やしても重ねない。** 増員は所要日数を縮める側にだけ効く（`definitions/20-scheduling-rules.md` 第2章 / 第4章）。

サーバ側の担当が1名の場合、基盤整備とサーバ側実装は並行させられない。直列に置く。

`resources.maxParallelTracks` に上限値を出力し、HTML の前提条件欄に表示する。

### 変更時の影響

- 上限を上げると期間は縮むが、実際の体制で回せない計画になりやすい。人数とセットで見直す。
- 「1役割が同時に持てる作業本数」を 2 以上にすると、同一担当のタスクが重なって配置され、ガント上で負荷の山が見えなくなる。

## 3. その他の稼働の前提

| 項目 | 既定値 | 備考 |
|---|---|---|
| 割り込み対応 | 実働係数に内包 | 別枠のタスクとしては置かない |
| レビュー待ち時間 | 各タスクに +0稼働日 | 大きい規模の案件のみ、「レビュー」を独立タスクとして置く |
| 連続稼働の上限 | 制限なし | 長期案件で連休を挟む場合は共通側の休業日一覧で表現する |
| 外部要因の待ち時間 | 個別に記載 | 外部サービスの審査待ちなどは「外部要因の待ち」のタスクとして明示する |

### 変更時の影響

- レビュー待ち時間を +1稼働日などに変えると、タスク数に比例して期間が伸びる。手戻りが多い案件では現実に近づく。
- 割り込み対応を別タスクとして立てる方針に変えると、ガントの行数が増え、実働係数は 1.0 に近づけることになる。
