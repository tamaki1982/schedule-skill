# かかる日数の基準

標準作業ごとの標準工数と、それに掛ける倍率。標準作業の一覧は `10-standard-tasks.md` にある。

## 1. 標準作業ごとの標準工数

| 標準作業 | 標準工数 | 上限側を採る条件 |
|---|---|---|
| 企画 | 2〜4人日 | 初めて開く形式の場合 |
| 確認・承認 | 1人日 | 確認する相手が3名以上、または社外を含む場合 |
| 制作 | 4〜7人日 | 制作物が3点以上ある場合。1点あたりではなく1まとまりあたり |
| 告知・集客 | 1〜2人日 | 配信先が複数ある場合 |
| リハーサル | 2〜3人日 | 出演者が3名以上いる場合 |
| 当日運営 | 3人日 | 当日の時間は固定。所要日数は1稼働日で置く |
| 振り返り | 3〜5人日 | アンケートの設問が10問を超える場合 |
| （予備日） | 0人日 | 標準作業ではない。量と位置は第3章 |

**書いてあるのは工数（人日）だけ。** 所要日数は `40-team.md` の人数と実働係数から式で出す
（`definitions/20-scheduling-rules.md` 第2章）。

```
有効人数 = 1 + (人数 − 1) × 0.7
所要日数 = ceil( 工数(人日) / (有効人数 × 実働係数) )
```

**当日運営だけは例外。** 開催日という1日に固定されるので、所要日数は常に1稼働日とし、工数だけを人日で持つ。

### 変更時の影響

- 制作の工数を増やすと、告知開始が後ろへ動く。開催日が固定の場合は着手日が前倒しになる。

---

## 2. 倍率

**倍率は工数に掛ける。所要日数には掛けない。** 複数該当する場合は掛け合わせる。

| 規模 | 倍率 |
|---|---|
| 小さい | 0.5 |
| 標準 | 1.0 |
| 大きい | 1.5〜2.0 |

| 条件 | 倍率 |
|---|---|
| 初めて開く形式（前例がない） | 1.3 |
| 社外の出演者・登壇者が関わる | 1.2 |
| 配信や中継を伴う | 1.2 |

---

## 3. バッファの量

| 種類 | 量 | 置き場所 | 置く条件 |
|---|---|---|---|
| 開催前の予備日 | 1〜2稼働日 | **開催当日マイルストンの中、開催日から日付が決まっている作業の並びの手前** | 常に置く |
| 告知前の予備日 | 1稼働日 | **告知開始マイルストンの末尾** | **告知開始マイルストンがある構成のときだけ置く。規模が「小さい」（構成 2-1）には置かない** |

**開催日は動かせないので、バッファは必ず開催の手前に置く。** 後ろには置けない。
当日運営は開催日に固定されているため、開催前の予備日はマイルストンの末尾ではなく**その手前**に入る
（`definitions/20-scheduling-rules.md` 第5章の、期日が固定された作業を含む場合の置き方）。

**固定されているのは当日運営だけとは限らない。** 前日リマインドのように**開催日を起点に日付が決まる作業**を
足した場合、それも固定された作業として扱い、**予備日はその並びのさらに手前に置く。**

```
標準構成どおり（固定は当日運営だけ）
  … 予備日 → 当日運営

前日リマインドを足した場合（固定が2つ続く）
  … 参加人数の確定と会場への連絡 → 予備日 → 前日リマインド → 当日運営
```

予備日を前日リマインドと当日運営の間に入れてはならない。前日リマインドが前日でなくなる。

**規模が「小さい」ときに告知前の予備日を置かないのは、その構成に「告知開始」という節目が無いため。**
告知・集客は準備の工程に含まれ、そこで遅れが出ても、後ろに続くのは開催当日マイルストンだけになる。
遅れは開催前の予備日で吸収できるので、予備日を2か所に分けても吸収できる量は変わらない。

### 変更時の影響

- 開催前の予備日を 0 にすると、リハーサルで見つかった問題を直す時間がなくなる。
- 置き場所を「当日運営の直前」という個別の作業名に戻すと、開催日を起点に固定される作業を足したときに、その作業が予備日の分だけ前へ押し出される。
- 規模が「小さい」ときにも告知前の予備日を置く運用にするなら、`20-structure.md` の構成 2-1 に告知開始マイルストンを足す必要がある。予備日だけを置くと、置き場所のないタスクになる。

## 4. 並行してよい組み合わせ

**この章のすべての行に、次の2つが先に効く。**

| 先に効く決まり | 内容 |
|---|---|
| **同じ役割のタスクは重ねない** | 並行してよい組み合わせであっても、担当が同じ役割なら直列に置く（`40-team.md` 第2章） |
| 同時本数の上限 | 同時に走らせられる作業本数を超えない（`40-team.md` 第2章） |

| 先に進むもの | 並行して進めてよいもの | 着手のタイミング |
|---|---|---|
| 制作（告知素材） | 制作（申込ページ） | 素材制作が半分進んだ時点 |
| 告知・集客 | 企画（当日の進行） | 告知の配信直後 |

**並べたあとに前後が逆転していないか確認する。**
後のタスクの開始日を先行タスクの開始日より前に置かない。

## 5. 直列にすべき組み合わせ

| 順序 | 理由 |
|---|---|
| 企画 → 確認・承認 → 制作 | 承認前に作ると作り直しになる |
| 制作 → リハーサル → 当日運営 | 資料が揃わないと通せない |
| 当日運営 → 振り返り | 実施しないと集計できない |

---

## 6. 同じ作業が繰り返し出るとき

同じ標準作業が1つのフェーズに2回以上出る場合（複数の制作物、複数チャネルへの告知など）、
**2回目以降の工数に係数を掛ける。**

| 何回目か | 工数に掛ける係数 |
|---|---|
| 1回目 | 1.0 |
| 2回目 | 0.7 |
| 3回目以降 | 0.5 |

下限は 0.5人日。数える範囲は同じフェーズの中。当日運営には適用しない。
適用したことを `meta.assumptions` に1行残す。
