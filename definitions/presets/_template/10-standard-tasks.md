# 標準作業

> この用途で繰り返し出てくる作業の型を並べる。**8〜12件**が目安。
> ここに書いた内容は**生成時に参照するだけ**で、出力される JSON には作業の名前しか残らない。
> 記入したら、この引用ブロックは削除する。

## 1. 標準作業の一覧

| 標準作業 | 既定の担当役割 | 並行可否 | 増員が効くか | 説明 |
|---|---|---|---|---|
| | | | | |
| | | | | |
| | | | | |

### 各列の書き方

| 列 | 決まり |
|---|---|
| 標準作業 | 日本語の作業名。**この文字列が JSON に入るわけではない**。生成時に、対象を足した具体的な名前へ展開する（第3章） |
| 既定の担当役割 | `40-team.md` に書いた役割のどれか。付けない場合は「（付けない）」 |
| 並行可否 | `並行可` または `直列`。`直列` にすると他タスクと期間が重ならないように配置される |
| 増員が効くか | `効く` / `そのまま効く` / `効かない` の3つ。既定は `効く`（`definitions/20-scheduling-rules.md` 第2章）。`そのまま効く` は、同じ作業を人数分そのまま同時にこなせる場合だけ（面接の枠、検品の台数など）。**迷ったら `効く`** |
| 説明 | その作業が何をするものか。1文 |

**この一覧に書いた作業は、`30-estimation.md` 第1章にも標準値の行を作る。**
作らないと、工数を推定で埋めることになる。

**縮められない待ち時間（相手の確認待ち、審査待ちなど）があれば、それも1件として置く。**
担当を付けず、工数 0 とする。**予備日とは別物**なので `isBuffer` は立てない（第2章）。

## 2. 予備日（バッファ）

**予備日は標準作業ではない。** 一覧に書かない。遅延を吸収するための空き時間であり、作業ではないため。

| 項目 | 値 |
|---|---|
| 表し方 | `isBuffer: true` |
| 工数 | 0人日 |
| 担当役割 | 付けない |
| 名前 | 何のための予備かが分かる名前にする |

**予備日は必ず置く。** 置かないと、遅れを吸収する余地が計画に残らない。
量と位置は `30-estimation.md` 第4章に書く。

版 5.0 まではバッファも作業の種別の1つとして扱っていたが、
版 6.0 でタスク種別を削除したため、`isBuffer` の真偽値だけで表す形になった。

## 3. 作業名の付け方

**画面に出るのは作業の名前だけ**なので、名前だけで意味が通る必要がある。
上の一覧の名前をそのまま使うと、同じ名前の行が複数のマイルストンに並んで区別が付かなくなる。

| 場面 | 付け方 |
|---|---|
| 工程を挟む形 | 工程名が上の行に出ているので、対象を繰り返さない |
| 工程を挟まない形 | **対象物を名前の先頭に置く**（例:「機能A 要件定義」） |
| 同じ作業が1つのフェーズに複数出る | 何についての作業かで区別する |

---

## 変更時の影響

- 行を追加・削除すると、生成されるスケジュールに出てくる作業が増減する。**出力の形は変わらない**（標準作業は JSON に載らないため）。
- 「並行可否」を `直列` に変えると、その作業は他と重ならないように配置され、全体の期間が伸びる。
- 「増員が効くか」を「効かない」に変えると、体制を増やしてもその作業の所要日数が縮まなくなる。
- 既定の担当役割を同じ役割に寄せると、並行実行が制限されて期間が伸びる。
