# 階層の定義

スケジュールは最大5つの階層で組み立てる。用途が変わってもこの階層の並びは変えない。

```
プロジェクト            … 取り組みそのもの。1つの HTML が複数持てる
  フェーズ              … プロジェクトの中の大きな括り
    工程                … 進め方の段階（省略できる）
      マイルストン      … 期日を持つ節目
        タスク          … 期間を持つ最小の作業
```

**工程は省略できる。** 省略したフェーズでは、フェーズの直下にマイルストンが並ぶ4階層になる。
どちらの形にするかは**フェーズごとに選ぶ**。1本のドキュメントの中で混在してよい。

**プロジェクトとフェーズは、どちらもツリーの行にならない。** どちらもプルダウンで選ぶ。
画面のツリーに並ぶのは、選ばれたプロジェクトの選ばれたフェーズの中身だけ。
データ上は5階層だが、**画面上は最大3段**。

---

## 1. 構成の形は2つある

| 形 | 構造 | JSON |
|---|---|---|
| **工程を挟む形** | フェーズ > 工程 > マイルストン > タスク | `phase.stages[]` |
| **工程を挟まない形** | フェーズ > マイルストン > タスク | `phase.milestones[]` |

**1つのフェーズが持てるのはどちらか一方だけ。** 両方を持つことも、どちらも持たないこともできない。
両方を許すと、工程の行とマイルストンの行が同じフェーズの中で並び、どちらが先に来るのかが決まらなくなるため。

### どちらを使うか

| 目安 | 使う形 |
|---|---|
| そのフェーズの中身を**進め方の段階**で分けたい（設計 → 実装 → 検証） | 工程を挟む |
| そのフェーズの中身を**機能や対象物**で括りたい（機能A / 機能B / 機能C） | 工程を挟まない |
| そのフェーズの中身が**同じ手順の繰り返し**（第1回 / 第2回 / 第3回） | 工程を挟まない |

判定に迷ったときは、**同じ工程名がそのフェーズの中で2回以上出てくることになるかを見る。**

出てくるなら、工程を挟まない形にする。
機能ごとに「要件定義・実装・テスト」を工程として置くと、工程の行が機能の数だけ繰り返され、
縦に長いだけで読み取れる情報が増えないスケジュールになる。
この場合は**マイルストンを機能単位に置き、その配下のタスク名に工程を持たせる。**

```
# 工程を挟まない形の例
フェーズ2
  機能A （マイルストン）
    要件定義 / サーバ側実装 / 画面側実装 / 動作テスト （タスク）
  機能B （マイルストン）
    要件定義 / サーバ側実装 / 動作テスト
  機能C （マイルストン）
    要件定義 / 画面側実装 / 動作テスト
```

機能ごとに含まれる作業が違っていてよい（上の例では機能Bに画面側実装が無い）。
工程を挟む形では全機能に同じ工程を並べることになり、この差を表せない。これも工程を挟まない形を選ぶ理由になる。

用途ごとの推奨は、各プリセットの `20-structure.md` にある。

## 2. 各階層が何を表すか

### プロジェクト (`projects[]`)

**取り組みそのもの。** 「これは何の話か」で分ける。

| 用途 | プロジェクトの例 |
|---|---|
| ソフトウェア開発 | 社内ポータル / 顧客向けアプリ |
| イベント運営 | ユーザーコミュニティ運営 / 月次オンライン勉強会 |
| 受託案件 | A社案件 / B社案件 |
| コンテンツ制作 | 動画シリーズ / 連載記事 |

判断の目安: **別々の相手・別々の目的・別々の始まりと終わりを持つか。** 持つなら別のプロジェクト。

**1つの HTML が複数のプロジェクトを持てる。** 画面ではプルダウンで切り替えて、一度に1つだけを見る。
束ねるかどうかの目安は次のとおり。

| 状況 | どうするか |
|---|---|
| 同じ体制で並行して回している複数の取り組み | **1つの HTML に束ねる。** 切り替えて見比べられる |
| 相手も体制も別で、見る人も別 | **HTML を分ける。** 束ねると、渡す相手に関係のないものまで見せることになる |
| 用途（プリセット）が違う | **HTML を分ける。** 1ドキュメント1プリセット（`00-index.md`） |

**1本のドキュメントにプロジェクトが1つしかないのは普通のこと。** 無理に分割しない。

プロジェクトの名前・目標・期間は、切替の操作の側と詳細パネルで見せる。

### フェーズ (`phases[]`)

**プロジェクトの中の大きな括り。** 「その取り組みのどの段か」で分ける。

| 用途 | フェーズの例 |
|---|---|
| ソフトウェア開発 | 初期開発 / リニューアル / 有料プラン対応 |
| イベント運営 | 事前告知 / 本開催 |
| 受託案件 | 初回契約分 / 追加契約分 |
| コンテンツ制作 | 第1シーズン / 第2シーズン |

判断の目安: **これ単体でも「やる / やらない」を決められる単位か。** 決められるならフェーズ。

1つのプロジェクトに1つしかフェーズが無いのも普通のこと。無理に分割しない。

#### フェーズは画面の表示単位でもある

**生成した HTML は、一度に1つのプロジェクトの1つのフェーズだけを表示する。**
残りは操作で切り替えて見る。このため、フェーズの区切り方が「1画面に何が見えるか」を直接決める。

```
（工程を挟むフェーズを選んだとき）        （工程を挟まないフェーズを選んだとき）
  工程                                      マイルストン
    └ マイルストン                              └ タスク
        └ タスク
```

| 項目 | 目安 |
|---|---|
| 1フェーズあたりの行数 | **40行程度まで**（工程行 + マイルストン行 + タスク行の合計） |
| 1プロジェクトあたりのフェーズ数 | 上限を置かない。ただし切替の選択肢が10を超えると選びにくくなる |
| 1ドキュメントあたりのプロジェクト数 | 上限を置かない。ただしフェーズと同じく、選択肢が増えると選びにくくなる |
| ドキュメント全体の行数 | 上限を置かない。プロジェクトとフェーズを増やしても1画面あたりの量は増えない |

**工程を畳んで縦を詰めることはできない。** 畳むと配下のマイルストンが1つも見えなくなるため、
画面側で工程の折りたたみを用意していない。**縦の量はフェーズの粒度で調整する。**

40行に収まらないフェーズは、次の順で検討する。

| 順 | 検討すること |
|---|---|
| 1 | **フェーズを2つに割れないか。** 上の判断の目安で切れるなら割る |
| 2 | **工程を挟む形をやめられないか**（第1章）。工程行の分だけ行数が減る |
| 3 | **タスクの粒度が細かすぎないか。** 1稼働日未満のタスクを並べていないか |

**割った結果フェーズが増えることを、悪いことと扱わない。** 切り替えて見るのだから、フェーズが多いほうが1枚あたりは読みやすい。
ただし**行数を減らすためだけの分割はしない。** 切替の選択肢に並んだときに、名前を見て何のことか分からないフェーズは作らない。

初期表示するプロジェクトとフェーズの決め方は `20-scheduling-rules.md` 第7章にある。

### 工程 (`stages[]`)

**進め方の段階。** 「どういう順で進めるか」で分ける。**省略できる。**

| 用途 | 工程の例 |
|---|---|
| ソフトウェア開発 | 設計 / 実装 / 検証 |
| イベント運営 | 企画 / 制作 / 告知 / 当日運営 / 振り返り |
| 受託案件 | ヒアリング / 見積 / 契約 / 制作 / 検収 / 納品 / 請求 |
| コンテンツ制作 | 企画 / 台本 / 収録 / 編集 / 公開 |

判断の目安: **前の段階が終わらないと次に進みにくい関係になっているか。** なっていれば工程。

工程の標準的な並びはプリセットの `20-structure.md` に定義する。ここでは並びを決めない。

### マイルストン (`milestones[]`)

**期日を持つ節目。** 配下のタスクが全部終わると迎える日を表す。
親は工程、工程を挟まないフェーズではフェーズになる。

| ルール | 内容 |
|---|---|
| 個数 | 工程を挟む形では1工程あたり1〜2個。工程を挟まない形では1フェーズあたり2〜6個。1フェーズ全体で3〜10個に収める |
| 日付 | 単一の日付 (`date`)。期間ではない。原則としてその親の最終タスクの終了日と一致させる |
| 判定可能性 | 「〜が完了している」で判定できる状態にする。「〜を進める」のような継続状態は置かない |
| 命名 | 到達した状態を表す体言止め。例: 「要件確定」「告知開始」「検収完了」「機能A 完成」 |
| 到達条件 | `exitCriteria` に2〜3項目、判定可能な形で書く |
| 成果物 | `deliverables` に、その時点で存在すべきものを列挙する |

マイルストンは**タスクの親**である。ガント上では、配下タスクをまとめた集約と、`date` 位置の旗の両方を持つ行として描かれる。
「このタスク群が終わるとこの期日を迎える」が見た目で分かるようにするための構造なので、
**タスクをマイルストンの外に置いてはならない。** タスクは必ずどれかのマイルストンに属する。

節目とは呼びにくい作業のまとまりであっても、期日を持つ形に言い換えて親を作る。

### タスク (`tasks[]`)

**期間を持つ最小の作業。** ガント上の1本の横棒に対応する。

| ルール | 内容 |
|---|---|
| 期間 | 開始日と終了日を持つ閉区間。両端とも稼働日 |
| 状態 | `status` を必ず書く（第4章）。**状態を人が入れるのはこの階層だけ** |
| 予備日 | 遅延吸収用のタスクは `isBuffer: true` とし、工数 0、担当役割なしで置く。これがタスクを分類する唯一の項目 |
| 担当 | `assigneeRole` は役割名。個人名は入れない |
| 粒度 | 1タスクは1〜15稼働日程度。これを超える場合は分割する（**分け方は `20-scheduling-rules.md` 第2章**。工数を分け、所要日数は分けない）。**工数 0 のタスク（縮められない待ち時間、予備日）はこの上限の対象外**。分割は工数を分ける手順であり、工数 0 では分けるものが無く適用できないため |
| 日程未定 | 決められない場合は `startDate` / `endDate` をともに `null` にする |
| 命名 | 工程を挟まない形では、タスク名に工程にあたる語を含めてよい。例: 「機能A 要件定義」 |

## 3. 期間未設定の扱い

日程を決められない要素は、消さずに `null` で残す。

| 階層 | 未設定の表し方 | ガント上の見え方 |
|---|---|---|
| マイルストン | `date: null` | 旗を持たない行 |
| タスク | `startDate: null` かつ `endDate: null` | バーを持たない行 |

初版の生成で `null` を作るのは、**入力文で言及されているが日程が判断できない場合に限る。**
言及されていないものを憶測で足して `null` にしない。

---

## 4. 親の期間・進捗・状態

プロジェクト・フェーズ・工程は `startDate` / `endDate` を持てるが、必須ではない。

**描画に使う期間は、宣言の有無にかかわらず常に配下から算出する。**

```
親の期間の開始 = 配下タスクの開始日の最小値と、配下マイルストンの期日の最小値のうち早いほう
親の期間の終了 = 配下タスクの終了日の最大値と、配下マイルストンの期日の最大値のうち遅いほう
```

配下マイルストンの期日を含めるのは、旗が親の集約の外に出る絵にならないようにするため。

`startDate` / `endDate` に書いた値は**想定の宣言**として扱う。生成時にはこの想定と配下の実期間を一致させて出力する。
その後の編集で配下が想定からはみ出した場合、**日程は止めず、はみ出していることを印で見せる。**
想定に合わせて配下を戻したり、想定を黙って書き換えたりしない。ずれていることが見えるのが目的であるため。

マイルストンは `date` のみを持ち、期間は持たない。マイルストンの「期間」は配下タスクから算出される。

**進捗率も状態も同じ扱いにする。** プロジェクト・フェーズ・工程・マイルストンの `progress` と `status` は、
**常に配下から算出**し、書かれている値は使わない。

状態の算出は次のとおり。

```
親の状態 =
  直下の子がすべて「完了」            → 完了
  1つでも「完了」または「進行中」がある → 進行中
  それ以外（すべて未着手）             → 未着手
```

下から順に積み上げる。マイルストンはタスクから、工程はマイルストンから、フェーズは工程（または直下のマイルストン）から、
プロジェクトはフェーズから決まる。

**親の `status` は生成時に書き出さない。** 期間の宣言と違い、「そのつもりだった」を残す意味が無く、
書けば算出値と食い違うだけになるため。

## 5. 階層をまたぐ関係

| 関係 | 表し方 |
|---|---|
| タスク間の前後関係 | `task.dependsOn[]` に `{ taskId, type, lagDays }` |
| マイルストン間の前後関係 | `milestone.dependsOn[]` に先行マイルストンの id |
| 工程間・フェーズ間・プロジェクト間の前後関係 | 持たせない。配下のマイルストンの依存で表す |

工程やフェーズに直接の依存関係を持たせないのは、粒度が粗すぎて日程の再計算に使えないため。
「実装が終わらないと検証に入れない」は、**実装工程の最後のマイルストンと、検証工程の最初のマイルストンの依存**として書く。

依存はフェーズをまたいでよい。**プロジェクトもまたいでよい**（`id` はドキュメント全体で一意なため、参照は id 1つで足りる）。
工程を挟む形のフェーズにあるタスクと、工程を挟まない形のフェーズにあるタスクの間にも張れる。

**要素を削除したときは、その要素を指していた `dependsOn` と `risks[].relatedIds[]` を必ず落とす。**
参照先が消えたまま残ると、そのデータは再生成や改版の入力として使えなくなる。

## 6. 識別子の接頭辞

| 階層 | 接頭辞 | 例 |
|---|---|---|
| プロジェクト | `prj-` | `prj-internal-portal` |
| フェーズ | `ph-` | `ph-initial-development` |
| 工程 | `st-` | `st-design` |
| マイルストン | `ms-` | `ms-requirements-fixed` |
| タスク | `tk-` | `tk-requirements-survey` |

内容部分は名称を英字化したもの。連番は使わない（要素が挿入されたときに番号が破綻するため）。

**`id` はドキュメント全体で一意にする。** プロジェクトをまたいだ重複も認めない。
画面も参照（`dependsOn` / `relatedIds`）も id 1つで対象を引くため、同じ id が2か所にあると引けなくなる。
別のドキュメントからプロジェクトを1件持ってくる場合は、**衝突する id を先に付け替える。**

## 7. 用語の言い換え

用途によっては「工程」「マイルストン」という呼び方が馴染まないことがある。
その場合、プリセットの `00-preset.md` の「用語の言い換え」に表示名だけを書く。
**JSON のキー名と階層の構造は変えない。** 変えるのは画面に出る言葉だけ。

## 変更時の影響

- 階層を増減すると、JSON スキーマ・HTML テンプレート・全プリセットの構成定義がすべて連動する。単独では変えられない。
- 「1つのフェーズが持てるのはどちらか一方だけ」を緩めて両方を許すと、工程の行とマイルストンの行の並び順を別途決める必要が出る。
- `id` の一意性をプロジェクト内に緩めると、`dependsOn` と `relatedIds` がプロジェクト id との組で持つ必要が出て、参照のすべてが2値になる。
- マイルストンの個数の上限を増やすと、生成される節目が細かくなり、ガントの行数が増える。
- 「マイルストンはタスクの親」をやめると、ガント上で「このタスク群が終わるとこの期日を迎える」が読み取れなくなる。この構造は意図的に選んだもので、崩さない。
- 親の期間を「宣言があればそちらを優先」に戻すと、配下を動かしても親が追随しなくなり、ガントの見た目が壊れる。
- 親の状態を「書かれた値を使う」に戻すと、タスクを1件完了にしても親の見た目が変わらなくなり、取り消し線が意味を持たなくなる。
- タスクの粒度の上限（15稼働日）を上げると、1本のバーが長くなり、進捗の実態が見えにくくなる。
- 工数 0 のタスクを上限の対象に戻すと、20稼働日を超える待ち時間を分割することになる。分ける工数が無いので、同じ待ちが2本のバーに割れるだけで、読み取れる情報は増えない。
