# 出力のルール

生成物をどこに、どういう名前で、どう出すか。用途に依存しない。

---

## 1. ドキュメント識別子

各ドキュメント（HTML 1枚とその元になる JSON 1本）には識別子 (`meta.id`) を1つ与える。

| 項目 | 規則 |
|---|---|
| 文字種 | 英小文字・数字・ハイフンのみ |
| 長さ | 2〜64文字 |
| 決め方 | 対象と内容を英字化してハイフンでつなぐ。例: `portal-virtual-office`、`user-community-programs` |
| 複数プロジェクトを束ねる場合 | **その束を表す名前にする。** 中の1プロジェクトの名前を使わない |
| 不変性 | 一度決めたら改版しても変えない。ディレクトリ名とファイル名の接頭辞になる |

同名の識別子が `output/` にすでに存在する場合、それは同じドキュメントの改版とみなす。
別物として扱いたい場合は識別子に区別を付ける。

**プロジェクトの識別子 (`project.id`) とは別物。** `meta.id` は HTML 1枚に1つ、`project.id` はその中に複数ありうる。

---

## 2. 表題は組み立てる (`meta.title` / `meta.groupName`)

**表題は考えて書かない。階層から機械的に組み立てる。**

```
プロジェクトが1件   : meta.title = <projects[0].name> + " スケジュール"
プロジェクトが2件以上: meta.title = <meta.groupName>  + " スケジュール"
```

| 項目 | 規則 |
|---|---|
| 区切り | **半角スペース1つ** |
| 接尾語 | **「スケジュール」で固定。** 用途によって変えない |
| どこに出るか | **ブラウザのタブと、印刷したときの見出しだけ。画面には出さない** |
| なぜ画面に出さないか | 画面には、いま見ているプロジェクト名とフェーズ名が2つのプルダウンに出ている。表題を並べると3つ目の名前が増える |
| 検証 | **組み立て結果と一致しているかを、不変条件 C18 で判定する** |

### まとめた呼び名 (`meta.groupName`)

**プロジェクトが2件以上のときだけ書く。** 複数の取り組みをまとめて何と呼ぶか。

| 項目 | 規則 |
|---|---|
| 必須になる条件 | **プロジェクトが2件以上のとき**（C19） |
| 書いてはいけない条件 | **プロジェクトが1件のとき**（C19）。書けると、プロジェクト名と違う名前を入れられてしまう |
| 決め方 | 依頼文に複数の取り組みをまとめて指す言葉があればそれを使う。無ければ、共通する対象か目的から作る |
| **使ってはいけない名前** | **中の1つのプロジェクト名。** 使うと、残りが資料の対象外に見える |

**これが、階層から自動では導けない唯一の名前。**
プロジェクト名を並べても束の名前は出てこない（「秋のユーザー交流会 / 月次オンライン勉強会」は列挙であって、呼び名ではない）。

### なぜ組み立てにするか

**人が書く欄にすると、階層と食い違っても誰も気づかない。**

```
実際に起きた例（表題を人が書いていたとき）
  表題      社内ポータル バーチャルオフィス機能 追加スケジュール
  プロジェクト 社内ポータル
  フェーズ    初期開発 / 機能拡張
            → 「バーチャルオフィス機能 追加」に当たる層がどこにも無く、
              読み手がその名前を探して見つけられない状態になっていた

組み立てにした後
  プロジェクト バーチャルオフィス機能追加        ← これを決めれば
  表題      バーチャルオフィス機能追加 スケジュール  ← これは自動で決まる
```

**製品名と取り組み名が両方あるときは、取り組みのほうをプロジェクト名にする。**
プロジェクトは「取り組みそのもの」を表す層であり（`10-hierarchy.md` 第2章）、製品名は `project.description` に書く。
上の例では「社内ポータル」が製品、「バーチャルオフィス機能追加」が取り組み。
**ここは人の判断が要るが、判断の対象はプロジェクト名1つに絞られ、表題はそこから従う。**

### 構成を変えたら組み直す

次のどれかに当たったら、表題を組み直す。

| 変えたもの | どうなるか |
|---|---|
| プロジェクトの名前（1件のとき） | **表題がそのまま変わる** |
| プロジェクトを増やした（1件 → 2件以上） | **`groupName` を新しく決める**（ここだけ判断が要る）。表題はそこから組み立てる |
| プロジェクトを減らした（2件以上 → 1件） | **`groupName` を削る。** 表題はプロジェクト名から組み立て直す |
| `groupName` | 表題がそのまま変わる |

### 変更時の影響

- 表題を人が書く運用に戻すと、階層と食い違っても誰も気づかない状態に戻り、C18 が判定できなくなる。
- 接尾語を用途ごとに変えられるようにすると、組み立て規則が1本でなくなり、一致判定に例外が要る。
- 表題を画面にも出す運用に戻すと、プロジェクト名・フェーズ名と並んで名前が3つ出ることになる。

## 3. 出力先とファイル名

```
output/
  <meta.id>/
    <meta.id>_r01_YYYY-MM-DD.json     スケジュールデータ（正）
    <meta.id>_r01_YYYY-MM-DD.html     閲覧用 HTML（単一ファイル）
    <meta.id>_r02_YYYY-MM-DD.json
    <meta.id>_r02_YYYY-MM-DD.html
    CHANGELOG.md                      改版履歴
```

| 要素 | 規則 |
|---|---|
| `r` の後ろ | `meta.revision` を2桁ゼロ埋めしたもの。初版は `r01` |
| `YYYY-MM-DD` | そのファイルを生成した日 |
| 拡張子 | JSON と HTML を必ず対で出力する。HTML 単体で出力しない |

**HTML は単一ファイルとして出す。** 外部のスタイル・スクリプト・データファイルを参照しない。
JSON は HTML の中に埋め込まれており、隣の `.json` はあくまで編集用の正データとして別に置く。
理由と埋め込みの手順は仕様書 2-9 にある。

**既存ファイルは決して上書きしない。** 改版は常に新しいファイルとして出力する。

### 変更時の影響

- ディレクトリ構成を変えると、`CHANGELOG.md` の参照パスも合わせて直す必要がある。
- 版数の桁を増やす (`r001`) と、既存ファイルとの並び順が混在する。切り替えるなら全案件で一斉に行う。
- HTML を単一ファイルでなくすと、受け取った人がファイルを直接開いたときに中身が読み込めなくなる（ローカルサーバが要る）。

## 4. 改版の規則

| 場面 | 版数の扱い |
|---|---|
| 日程の変更 | +1 |
| 要素の追加・削除 | +1 |
| 表記のみの修正（名称、説明文） | +1 |
| **生成し直し（同じ入力で再実行）** | **中身が変わるなら +1。変わらないなら出し直さない**（下記） |
| **利用者が JSON ファイルを直接書き換えた** | **据え置き。同じファイルを書き換える。次の改版時に取り込む（下記）** |
| **HTML 上での編集** | **据え置き。保存されないため、ファイルには何も残らない** |

改版時は以下をすべて行う。

1. 直前の版の JSON を読み込み、それを起点に編集する。ゼロから作り直さない。
2. 変更しない要素の `id` は必ず維持する。`id` が変わると差分が追えなくなる。
3. `meta.revision` を +1、`meta.generatedAt` を現在時刻、`meta.sourceRequest` を今回の修正指示文、`meta.previousRevisionFile` を直前の版の JSON ファイル名に更新する。
4. `calendar.today` を現在日に更新する。
5. `changeLog` に今回のエントリを1件追記する。既存のエントリは書き換えない。
6. `CHANGELOG.md` に1行追記する。

**`changeLog` はドキュメントに1本。** プロジェクトごとには持たない。
どのプロジェクトの話かは `changes[].targetId` から辿れる。

### 生成し直しの扱い

同じ依頼をもう一度流す場面は2つあり、**扱いが分かれる。**

| 場面 | どうするか |
|---|---|
| **定義ファイルや前提を直したあと、その効果を確かめるために作り直す** | **改版として扱う（+1）。** `changeLog[].instruction` に、再生成であることと理由を書く（例:「予備日の置き場所の定義を直したため再生成」） |
| **中身が1つも変わらない作り直し**（同じ定義・同じ入力） | **出し直さない。** すでにある最新版のファイルがそのまま答えになる。開くべきファイルの絶対パスを伝えて終える |
| 前の版のファイルを失った・壊した | **同じ版数で出し直してよい。** 出力先に何も無いので衝突しない |

**「版数据え置きで、新しい日付のファイルを出す」運用は取らない。**
ファイル名は `<識別子>_r<版数2桁>_<日付>` なので、**この運用は翌日以降にしか成立しない。**
同じ日に作り直すと必ずファイル名が衝突し、`build.py` は上書きせず止まる。
そして**定義を直した直後に効果を確かめる場面が、ちょうどこの経路に入る。**
再生成の理由になるのはたいてい「何かを直したから」であり、そのときは中身が変わっている。
**中身が変わったなら改版である**、と1本の規則に寄せたほうが、日付に左右されずに済む。

### `changeLog[].summary` に書くこと

**その版で何をしたかだけを書く。1〜2文。**

| 書く | 書かない |
|---|---|
| 何を変えたか（「実装工程を2週間後ろ倒しし、公開日を 12/11 に変更」） | **構成の数え上げ**（「プロジェクト2件・フェーズ3件・タスク26件」） |
| なぜ変えたか（指示の要点） | リスクや前提の説明（`risks` / `meta.assumptions` に書く） |
| 手編集分を取り込んだこと | 変更の全件列挙（`changes[]` に書く） |

**構成の数え上げを書かない理由**: `changeLog` は設定ファイルビューに出るが、
**画面はいま見ているフェーズの分だけを表示する。** 「プロジェクト2件」と書いてある履歴が、
1フェーズ分だけを切り出した資料に付いてくると、読んだ人には無い物を探させることになる。
**履歴は「そのときやったこと」であって、いまの中身の説明ではない。**

構成の数え上げが要る場合は、**ファイル側の `CHANGELOG.md` に書く**（下の形式）。こちらは資料全体の履歴なので数えてよい。
初版の `summary` は「（初版）〈対象〉のスケジュールを作成」で足りる。

### CHANGELOG.md の形式

```markdown
# <meta.title> 改版履歴

| 版 | 日付 | 修正指示 | 変更内容 |
|---|---|---|---|
| r02 | 2026/09/12 | 実装工程を2週間後ろ倒し | バッファを2稼働日消費、公開日を 2026/12/11 へ変更 |
| r01 | 2026/09/05 | (初版) | プロジェクト1件・フェーズ2件・工程3件・マイルストン9件・タスク26件で作成 |
```

新しい版を上に積む。

### 直接書き換えられた JSON の扱い

利用者は、最新版の JSON ファイルをエディタで直接書き換えることがある。誤字の訂正、担当役割の変更、状態の更新などが該当する。
この書き換えでは版数を上げない。1項目直すたびに版が増えると、どれが最新か分からなくなるため。

**次に改版を行うとき、起点にした JSON の `changeLog` と実データが食い違っている場合がある。**

| 場面 | 扱い |
|---|---|
| `changeLog` の最新エントリと実データが合わない | **実データを正として扱う。** `changeLog` を信用して実データを戻さない |
| 食い違いに気づいた | 今回追記する `changeLog` エントリの `summary` に、直接の書き換え分を取り込んだ旨を1文添える |
| 食い違いの内容が大きい（構造が変わっている等） | 処理を止めず進めるが、何が食い違っていたかを報告に含める |

### 変更時の影響

- 「表記のみの修正で版を上げる」をやめると、ファイル数は減るが、いつ何を直したか追えなくなる。
- 生成し直しを「版数据え置き」に戻すと、同じ日に2回目を流した時点でファイル名が衝突し、出力できなくなる。
- `id` の維持を外すと、改版のたびに全要素が別物として扱われ、変更履歴が意味を持たなくなる。
- 直接の書き換えでも版を上げる規則に変えると、履歴は正確になるが、小さな訂正のたびにファイルが2つ増える。

## 5. 日付の表記

| 対象 | 形式 |
|---|---|
| JSON 内のデータ | ISO 8601 (`2026-11-27`) |
| ファイル名 | ISO 8601 (`2026-09-05`) |
| HTML 上の表示 | スラッシュ区切り (`2026/11/27`) |
| ドキュメント本文 | スラッシュ区切り (`2026/11/27`) |

### 変更時の影響

- HTML 上の表示形式を変える場合は、テンプレート側の整形処理を直す。JSON のデータ形式は変えない。

## 6. 出力に含めない情報

生成する JSON・HTML・定義ファイルには以下を書かない。

| 書かないもの | 代わりに |
|---|---|
| 個人名 | 役割名で表す（`assigneeRole` に「制作」「検証」など） |
| **実在の会社名・製品名（依頼で明示された対象を除く）** | 一般名で表す。定義ファイルとサンプルには実在の名前を一切書かない |
| 生成の過程や使用したツールに関する記述 | 書かない |
| 話し言葉、くだけた言い回し | 淡々とした記述にする |
| 絵文字を使った補足コメント | 書かない。**マイルストンの旗は絵文字ではなく図形としてテンプレートが描くもので、データには持たせない** |

出力物は、そのまま社外の相手に見せられる状態であることを前提とする。

**`meta.sourceRequest` と `meta.assumptions` は設定ファイルビューに出る。**
生成した HTML を社外へ渡す場合、この2つに内輪の事情が書かれていないかを渡す前に確認する。

**設定ファイルビューから切り出した範囲を渡す場合も、同じ確認が要る。**
画面は表示中のフェーズだけを出すが、**`meta` は切り出した出力にもそのまま入る**（仕様書 6-10）。
**構造は絞れても、文章の中身は絞れない。**
たとえば `meta.assumptions` に「取り組みが2つに分かれているため、プロジェクトを2件に分けた」と書いてあれば、
1フェーズ分だけを渡したつもりでも、**他のプロジェクトがあることは相手に伝わる。**

### 定義ファイルを HTML に含めるかどうか

**生成した HTML には、この資料を作るのに使った定義ファイルの中身を一切埋め込まない
（配布版の判断。2026/09/07以降）。** 埋め込む・埋め込まないを出力ごとに選ぶ仕組み自体を
やめてあるので、`build.py` にフラグを渡す必要は無い。どの定義バージョンで作ったかだけは
`meta.definitionsVersion` に残る（`00-index.md` の版）。

**定義ファイルには、その組織の見積もり基準・体制・実働係数・分野の考え方が入る。**
とくに `50-user-context.md` はまるごと組織の内情、`30-estimation.md` と `40-team.md` は
原価の作り方に近い情報になる。**埋め込みをやめたのは、見えない・誰も見ない情報を
出力ファイルに積んでおく理由が無く、渡す相手を都度判断する運用そのものをなくすため。**

### 変更時の影響

- 埋め込みを復活させる場合、`build.py`（定義ファイルの読み込み・JS変数への組み込み）と
  `templates/schedule.template.html`（表示・編集・書き出しの画面）の両方に作り直しが要る。
  2026/09/07 以前の実装（`git` 履歴、または `dev/_archive/` の旧版）が参考になる。
- 定義ファイルの中身をその場で確かめたい相手には、この資料からは確かめられない
  （`definitions/` のファイルを別途渡す必要がある）。

## 7. 報告に含めること

生成・改版が終わったら、次を利用者に伝える。

| # | 内容 |
|---|---|
| 1 | 出力した HTML の絶対パスと、それを開くコマンド |
| 2 | 出力した JSON の絶対パス |
| 3 | 採用したプリセットと、その理由 |
| 4 | **表題（`meta.title`）。複数プロジェクトならまとめた呼び名（`meta.groupName`）も** |
| 5 | **プロジェクトの一覧と、最初に開くプロジェクト** |
| 6 | **プロジェクトごとのフェーズの一覧と、最初に開くフェーズ** |
| 7 | 採用した前提（`meta.assumptions` の内容） |
| 8 | 記録したリスク |
| 9 | 検証の結果 |
| 10 | **目標日に間に合わせるために既定の体制を増やした場合は、どの役割を何名にしたか。増やせない場合に何稼働日届かないか** |
| 11 | **増員と並行化でも間に合わなかった場合は、何稼働日不足しているか** |
| 12 | 「今日」がタイムラインの範囲外にある場合は、その旨（画面に今日の線が出ない） |
| 13 | （改版時のみ）全体の終了日が変わったかどうか、変わった場合は変更前後の日付 |
| 14 | （改版時のみ）バッファの残量。0 になった場合はその旨を明示する |
| 15 | **置き場に書き換えた定義ファイルがあり、既定値のほうが新しい場合は、どのファイルがどの版のまま止まっているか。** その間に既定値で何が変わったか。既定値に戻す方法（置き場のそのファイルを消す） |

**15 を必ず伝える理由**: 書き換えた定義ファイルは、配布側の更新を受け取らない。
**これは意図した動きだが、黙っていると「直したはずの不具合が直っていない」という形で現れる。**
**実際に、置き場の古いコピーを読んでいたことに、使う側にも配る側にも気づけなかったことがある。**
どちらの版を使うかは利用者が決めてよい。**知らせずに使わせることだけを避ける。**

**全体の終了日が動いたことを黙って報告から落とさない。**

### 検証が通らずに止まった場合の報告

**出力が1つも無いまま終わることがある**（仕様書 4章 Step 6 の歯止め）。このときは上の表ではなく、次を伝える。

| # | 内容 |
|---|---|
| 1 | **出力できなかったこと**（HTML も JSON も `output/` に無い） |
| 2 | 何回やり直したか、なぜ止めたか（**同じエラーが続いた** / 3回で通らなかった） |
| 3 | **最後に残ったエラーの全文。** 要約しない |
| 4 | **人がどこを直せばよいか。** 依頼の内容か、定義ファイルか、こちらの文書の矛盾か |
| 5 | **最後に作った JSON の絶対パス**（消さない。人が直して `build.py` に渡し直せる） |

**「作れませんでした」だけで終わらせない。** 受け取った人はこの仕組みを知らないので、
**次に何をすればよいかまで書いて初めて報告になる。**

**増員を前提にした計画は、必ず言葉でも伝える。** タイムライン上は間に合っているため、
黙っていると「いまの体制で間に合う」と受け取られる。**間に合わせるために何が要るかまでが答えである。**

**プロジェクトとフェーズの一覧を必ず伝える理由**: 画面には一度に1つのプロジェクトの1つのフェーズしか出ない。
他に何があるかを言葉でも伝えておかないと、
開いた人が「頼んだ内容の一部しか作られていない」と受け取ることがある。
**プロジェクトが増えたぶん、この行き違いは起きやすくなっている。**

**表題を4番目に置いて、一覧のすぐ上に並べる理由**: 表題が組み立てになった今も、
**`groupName` とプロジェクト名の中身が実態に合っているかは機械では判定できない。**
**報告で並べて見せれば、読んだ人が気づける。** 実際、この規定は表題だけが階層と食い違った出力が出たことを受けて足した。

---

## 8. `meta.notes` に書くこと

**この資料を読む人への注意書き。0〜3件。空でよい。**
`meta.subtitle` を廃止したときに、補足の行き先としてこの欄を残した。何でも入る欄になりやすいので、置く基準を決めておく。

| 書く | 書かない |
|---|---|
| この資料が扱っていない範囲（「保守運用は含まない」） | **前提** → `meta.assumptions` |
| 読み違えやすい点（「日付はすべて稼働日で数えている」） | **リスク** → `risks` |
| 表題や呼び名の補足（「〈まとめた呼び名〉は社内での通称」） | **変更の履歴** → `changeLog` |
| 資料の使い方（「フェーズを切り替えて見る」） | 内輪の事情、担当者の名前、生成の過程 |

**迷ったら書かない。** 1件も無いのが普通の状態。
`meta.notes` は設定ファイルビューに出るので、社外へ渡す前に第6章の確認をする。

### 変更時の影響

- 基準を緩めると、前提・リスク・履歴が3か所に散り、どこを見れば正なのか分からなくなる。
