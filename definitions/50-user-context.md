# 利用者の前提

**この一式を使う人・組織のやり方を書く場所。** 用途（開発・イベント・受託・制作・採用…）が変わっても
変わらない決まりだけを置く。既定値が入っているので、**何も書き換えなくてもそのまま動く。**
合わないところだけ直せばよい。

---

## 0. どこに何を書くか

この一式は3つの層でできている。

```
骨格          … 用途にも人にも依存しない（階層の定義、日程の組み方の原則、出力の形）
利用者の前提   … その人・その組織に固有。用途をまたいで効く          ← このファイル
プリセット     … 用途ごと（開発 / イベント / 受託 / 制作 / 採用 …）
```

迷ったら次の1問で決める。

| 問い | 答え | 書く場所 |
|---|---|---|
| 用途が変わってもその決まりは変わらないか | 変わらない | **このファイル** |
| 用途が変わってもその決まりは変わらないか | 用途ごとに違う | プリセットの該当ファイル |
| その案件かぎりの話か | そう | 入力文で伝える（ファイルに書かない） |

例:「うちは常に週4稼働で見積もる」「社外に出す成果物には必ず5営業日の確認待ちを置く」は、
開発でもイベントでも同じように効くので**このファイル**。
「配信ストアの審査は3〜10稼働日かかる」は開発でしか出てこないので**プリセット**。

### 優先順位

```
入力文の明示的な指定  >  利用者の前提  >  プリセット  >  骨格  >  推定
```

**このファイルとプリセットが食い違ったら、このファイルが勝つ。**
配布されたプリセットは一般的な目安であり、こちらは使う人が自分の実態に合わせて書いた値であるため。

ただし**骨格の階層の定義と出力のルールは、このファイルでも覆せない。**
ここで変えてよいのは「どれくらいかかるか」「何を必ず入れるか」「どうまとめるか」「何と呼ぶか」であって、
「どういう構造で出すか」ではない。

### 書き換え方

- 表の**値だけ**を書き換える。行や章は消さない（消すと、既定に戻ったのか未記入なのか分からなくなる）。
- `（未設定）` と `（なし）` は「骨格とプリセットの値をそのまま使う」という意味。
- 書き換えたら、このファイル冒頭の「最終更新」を直す。
- 生成のたびに読まれるファイルなので、**長い文章を書かない。** 表と短い箇条書きで済ませる。

| 項目 | 値 |
|---|---|
| 最終更新 | 2026/09/07 |
| 状態 | **既定のまま（未カスタマイズ）** |

**章の一覧**: 1 この組織のこと / 2 稼働の前提 / 3 目標日への向き合い方 / 4 標準作業の束ね方 /
5 どの用途でも必ず入れるもの / 6 呼び方 / 7 資料に書かないこと / **8 画面の見え方の既定**

## 1. この組織のこと

スケジュールの前提を推定するときの手がかりになる。埋めなくても動くが、埋めるほど推定が当たる。

| 項目 | 値（既定） |
|---|---|
| 分野・業種 | （未設定） |
| スケジュールを見せる相手 | 社内 |
| 意思決定の仕方 | （未設定。例:「担当者の判断で進む」「毎週の定例で承認される」） |
| よく使うプリセット | （未設定） |

**この分野で当たり前になっていること**（生成時にそのまま前提として使われる）:

-

### 変更時の影響

- 「見せる相手」を社外にすると、内輪の事情を `meta.assumptions` に書かない判断が強く働く。
- 「当たり前になっていること」に書いた内容は、`meta.assumptions` に前提として転記される。

## 2. 稼働の前提

| 項目 | 値（既定） |
|---|---|
| 稼働曜日 | 月〜金（骨格の既定のまま） |
| この組織だけの休業日 | （なし） |
| **この組織だけの例外稼働日** | **（なし）** |
| 実働係数の扱い | プリセットの値をそのまま使う |
| 1役割あたりの人数の上限 | **既定の人数の3倍まで、かつ5名まで**（目標日に間に合わせるために増やす場合の上限） |
| 同時に走らせられる作業本数の上限 | プリセットの値をそのまま使う |

「この組織だけの休業日」に書いた日付は、暦の祝日（`20-scheduling-rules.md` 第1章の一覧）に**足して**扱う。
創立記念日、一斉休業、閑散期の短縮稼働などが該当する。

「この組織だけの例外稼働日」は逆で、**土日祝でも毎年必ず稼働する日**を書く。
書いた日付は `calendar.exceptionalWorkingDays` に入り、**営業日として数えられる。**
案件ごとの休日作業（イベント本番など）はここではなく、そのつど入力文で伝える。

### 変更時の影響

- 稼働曜日を減らすと、同じ工数でも全案件の期間が伸びる。
- 人数の上限を上げると、間に合わない案件で「増員すれば間に合う」計画が出やすくなる。実際に人を出せない体制で上げない。
- 例外稼働日を足すと、その日を含むタスクの所要日数が全案件で1日ずつ増える。

## 3. 目標日への向き合い方

| 項目 | 値（既定） |
|---|---|
| 目標日に間に合わない見込みのとき | **間に合う計画を出す。** 必要な増員・並行化を前提とリスクに明記する |
| 詰める順番 | 並行化 → 増員 → それでも足りなければ超過を出す |
| バッファを削って辻褄を合わせる | **しない** |
| バッファの厚み | プリセットの値をそのまま使う |

手順は `20-scheduling-rules.md` 第3章にある。ここで変えられるのは方針だけ。

**「実態を優先する」に変えたい場合**は、1行目を「期間が足りないことをそのまま出す」に書き換える。
その場合、増員も並行化も行わず、着手日を今日に固定した超過ありの計画が出る。

### 変更時の影響

- 「間に合う計画を出す」から「実態を優先する」に変えると、目標日を超えた計画がそのまま出るようになる。
- 詰める順番から「増員」を外すと、体制を動かせない組織では現実に近づくが、超過する案件が増える。

## 4. 標準作業の束ね方（粒度）

**同じ作業を1本で出すか、分けて出すか。** 用途を問わず常にそうしているものだけをここに書く。

| 項目 | 値（既定） |
|---|---|
| 束ねる指定 | （なし。プリセットの標準作業をそのまま1作業＝1タスクとして出す） |

書き方は次の形にそろえる。

```
<標準作業A> と <標準作業B> を「<まとめた名前>」として1本にする
```

束ねたときの扱い:

| 項目 | どうなるか |
|---|---|
| 工数 | 束ねた作業の工数を合算する |
| 担当役割 | 後段の作業の役割を使う |
| 増員が効くか | 片方でも「効かない」なら、束全体を「効かない」として扱う |
| 依存 | 束の内側の前後関係は消える。外側との依存は束に付け替える |
| 名前 | まとめた名前に対象を足す（例:「〈対象〉 バックエンド開発」） |

### どちらに書くかの例

「バックエンド設計とバックエンド実装を、バックエンド開発として1本で出したい」という指定は、
**3か所のどこにでも置ける。** 置く場所で効く範囲が変わる。

| 言いたいこと | 置く場所 |
|---|---|
| **うちは用途を問わず、設計と実装は常に1本にする** | **このファイル（第4章）** |
| ソフトウェア開発ではまとめるが、他の用途では分ける | プリセットの `10-standard-tasks.md` と `20-structure.md` |
| 今回の案件だけまとめてほしい | 入力文で伝える |

3か所すべてに書いてあっても壊れない。**優先順位（第0章）で、入力文 → このファイル → プリセットの順に勝つ。**

### 変更時の影響

- 束ねると行数が減って全体が読みやすくなるが、どこまで進んだかの見え方は粗くなる。
- 束ねた作業が「増員が効かない」側に寄るため、増員で期間を詰めにくくなる。

## 5. どの用途でも必ず入れるもの

用途に関係なく、毎回必ず計画に置く作業や待ち時間。

| 何を置くか | 期間 | どこに置くか |
|---|---|---|
| （なし） | | |

書き方の例:

| 何を置くか | 期間 | どこに置くか |
|---|---|---|
| 取引先・関係者の確認待ち | 5営業日 | 社外に出す成果物のマイルストンの直前 |
| 上長の承認 | 2営業日 | 各フェーズの最後 |

ここに書いたものは、**担当役割を付けず、工数 0 の独立したタスク**として置く（予備日ではないので `isBuffer` は立てない）。

### 変更時の影響

- 行を足すと、その待ち時間の分だけ全用途で期間が伸びる。実態に合っていれば、伸びるのが正しい。

## 6. 呼び方

画面に出る言葉を、組織で使っている言い方にそろえたい場合に書く。

| 階層 | この組織での呼び方（既定は空欄＝そのまま） |
|---|---|
| プロジェクト | |
| フェーズ | |
| 工程 | |
| マイルストン | |
| タスク | |

**プリセットの「用語の言い換え」と食い違ったら、こちらが勝つ。**
**画面に出る言葉だけが変わる。** JSON のキー名も階層の構造も変わらない。

### 変更時の影響

- 呼び方を変えても、過去に作った資料の中身は変わらない。並べても壊れない。

---

## 7. 資料に書かないこと

骨格（`30-output-rules.md` 第6章）の決まりに、この組織で足したいものがあれば書く。

| 書かないもの | 値（既定） |
|---|---|
| 個人名 | 書かない（骨格の決まり） |
| 実在の会社名・製品名 | 依頼で明示された対象だけ書く（骨格の決まり） |
| この組織で足したいもの | （なし） |

### 変更時の影響

- 行を足すと、その情報が `meta.assumptions` や `notes` から落とされる。落とした結果、前提の説明が足りなくなっていないかは人が見る。

## 8. 画面の見え方の既定

**新しく作るスケジュールを、開いた直後にどう見せるか。** ここで決めた値が `display` に書き出される。

| 項目 | 値（既定） | 取りうる値 |
|---|---|---|
| タスクのバーの色 | `accent` | `accent`（薄い黄）/ `cool` / `warm` / `purple` / `neutral` |
| 休みの日の列に色を付ける | 付ける | 付ける / 付けない |
| 土日祝にも日程を置けるようにする | しない | する / しない |

**「取りうる値」の側から1つ選んで、値の欄を書き換える。** 表の行は消さない（第0章の書き方）。

**3つとも、出来上がったスケジュールの画面（設定の歯車）でその場で変えられる。**
ここに書くのは**次に作るときの出発点**であって、既に作った資料は変わらない。

| どこで変えるか | 何に効くか |
|---|---|
| **このファイル** | **次に作るスケジュール** |
| **画面の設定（歯車）** | **いま開いている資料1本** |

**「土日祝にも日程を置けるようにする」を「する」にしても、生成が休日に日程を置くようにはならない。**
これは**画面で編集するときに休日へ置けるかどうか**の設定。
生成側が休日を使うのは、依頼文に根拠があるときだけ（`20-scheduling-rules.md` 第1章）。

### 変更時の影響

- バーの色を変えても、日程・所要日数・検証の結果は1つも変わらない。紙の対応表の色も一緒に変わる。
- 「休みの日の列に色を付ける」を「付けない」にすると、日単位で開いたときの縦縞が消える。日数の計算は変わらない。
- 「土日祝にも日程を置けるようにする」を「する」にすると、画面でバーを休日へ動かせるようになり、
  **動かした日がその計画の営業日として数えられる**（`calendar.exceptionalWorkingDays` に足される）。
  切り戻しても、足した日は残る。
