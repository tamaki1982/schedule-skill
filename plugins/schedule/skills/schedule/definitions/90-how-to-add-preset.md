# 新しい用途のプリセットを足す手順

このツールは、スケジュールの「組み立て方」と「その分野の中身」を分けて持っている。
新しい分野のスケジュールを作りたくなったら、**中身のほうだけを1セット足せばよい。** 組み立て方には触らない。

営業活動でも、採用の進行でも、社内ルールの整備でも、同じやり方で足せる。

**この一式を受け取った人が、自分の分野を足すための手順でもある。**
インストールも設定も要らない。フォルダをコピーして、テキストを6つ埋めるだけ。

---

## その前に: プリセットに書くことか、そうでないか

足す前に1つ確認する。**用途が変わっても変わらない決まりは、プリセットではなく `50-user-context.md`（利用者の前提）に書く。**

| 決めたいこと | 書く場所 |
|---|---|
| その分野に出てくる作業・進む順番・かかる日数 | **プリセット**（このファイルの手順） |
| うちは常に週4稼働、社外提出には必ず5営業日の確認待ち、設計と実装は常に1本にまとめる | **`50-user-context.md`** |
| 今回の案件だけの事情 | 入力文で伝える（ファイルに書かない） |

用途ごとに書き分ける必要のないものをプリセットに書くと、**用途を足すたびに同じことを書き写すことになる。**

---

## 何を足すことになるのか

足すのは、次の6つの問いに答えたファイル1セットだけ。

| # | 問い | ファイル |
|---|---|---|
| 1 | この用途は、どういう依頼のときに使うのか | `00-preset.md` |
| 2 | どんな作業が出てくるのか | `10-standard-tasks.md` |
| 3 | どういう順番で進むのか | `20-structure.md` |
| 4 | それぞれ何日くらいかかるのか | `30-estimation.md` |
| 5 | 誰が、どれくらいの時間を使えるのか | `40-team.md` |
| 6 | この用途ならではの注意点は何か | `50-domain-notes.md` |

日付の計算、休業日の扱い、目標日からの逆算、間に合わないときの詰め方、出力の形式は、すべて共通側が面倒を見る。
**あなたが書くのは、この6つの答えだけ。**

---

## 手順

### Step 1. 名前を決める

英小文字・ハイフンだけの短い名前を1つ決める。これがフォルダ名になる。

例:
- 営業活動 → `sales-pipeline`
- 採用の進行 → `hiring-process`
- 社内ルールの整備 → `internal-policy`

### Step 2. 雛形をコピーする

`definitions/presets/_template` を、同じ `presets/` の下に、決めた名前でコピーする。

```
definitions/presets/_template  →  definitions/presets/<決めた名前>
```

（一式をどこに置いているかは人によって違うので、ここでは相対の位置だけを書く。）

### Step 3. 6つのファイルを埋める

コピーしたフォルダの中の6ファイルを、上から順に埋める。
各ファイルの冒頭に「ここに何を書くか」が書いてあるので、それに従う。

一度に完璧にしなくてよい。**最初は 10 / 20 / 30 の3つだけ埋めて、40 と 50 は既定のままでも動く。**

### Step 4. （任意）索引に1行足す

`definitions/00-index.md` の「プリセット一覧」の表に、追加した行を書く。

```markdown
| `sales-pipeline` | 営業活動の進行管理 | 簡易 |
```

**書かなくても動く。** 選択肢は `presets/` 直下のフォルダを見て決まるので、フォルダを置いた時点で使える。
この表は一覧として見やすくするためのもの。**一式を更新したときに衝突しやすい場所なので、無理に書かなくてよい。**

### Step 5. 試しに1本作らせる

その用途の依頼文を1つ与えて、スケジュールを生成させる。
出てきたものを見て、次の順で直す。

| おかしいところ | 直すファイル |
|---|---|
| 出てくる作業が違う・足りない | `10-standard-tasks.md` |
| 進む順番が違う | `20-structure.md` |
| 各作業の長さが合わない | `30-estimation.md` |
| 全体的に楽観的すぎる・悲観的すぎる | `40-team.md` の実働係数 |
| その分野特有の事情が反映されていない | `50-domain-notes.md` |

2〜3回直せば実用になる。

---

## 書くときのコツ

### 標準作業（`10-standard-tasks.md`）

**8〜12件**にとどめる。多すぎると使い分けられず、少なすぎると全部「その他」になる。

「準備」「本番」「後片付け」のような大雑把な括りで始めて、
実際に生成させてみて足りないと感じたときに割る、という順がやりやすい。

**ここに書いた内容は出力される JSON には載らない。** 生成時に参照するだけなので、
足しても減らしてもスキーマにも出力の形にも影響しない。**気軽に育ててよい。**

**縮められない待ち時間（相手の確認待ち、審査待ちなど）があれば、それも1件として置く。**
担当を付けず、工数 0 とする。これを置かないと、実態より短い日程が出る。

**予備日（バッファ）は標準作業の一覧に書かない。** 作業ではないため。
`isBuffer: true` で表し、量と位置は `30-estimation.md` に書く。**置くこと自体は必須**で、
置かないと遅れを吸収する余地が計画に残らない。

**タスクの種別（分類）は無い。** 作業を分類したくなっても、種別の列を勝手に足さない。
分類が要ると判断する材料が出てきたら、仕様書の 8-2 の 27 で扱う。

**状態（未着手 / 進行中 / 完了）はプリセットで定めない。** 骨格が3値で固定しており、
用途によって語彙が変わるものではない。呼び方だけを変えたい場合は `00-preset.md` の「用語の言い換え」に書く。

### 進む順番（`20-structure.md`）

「規模が小さいとき」「普通のとき」「大きいとき」の3つを書く。
面倒なら**「普通のとき」1つだけでもよい。** その場合、規模に関わらず同じ骨格が使われる。

### かかる日数（`30-estimation.md`）

正確な値を出そうとしない。**過去に1回やったときの実感**を書けば足りる。
ずれていたら、生成結果を見てから直せばよい。

範囲で書くとき（「5〜8日」など）は、**どちらを採るかの条件を必ず添える。**
添えないと、毎回違う値が出て比べられなくなる。

### 誰がやるか（`40-team.md`）

「実働係数」は、1日のうちその案件にどれだけ使えるかの割合。
- 専任なら 0.8（会議や問い合わせで2割は消える前提）
- 他の仕事と半々なら 0.4〜0.5
- 片手間なら 0.2〜0.3

**ここが日程に一番効く。** 見積もりが常に甘いと感じたら、作業日数ではなくここを下げる。

### その分野の注意（`50-domain-notes.md`）

「この分野では、これを忘れると必ず事故る」というものを書く。

例:
- 受託案件 → 相手の確認待ちは自分たちで縮められない
- イベント → 会場や配信の予約は早い者勝ちで、後ろ倒しができない
- コンテンツ制作 → 出演者や取材先の都合で日程が動く

## やってはいけないこと

| やらないこと | 理由 |
|---|---|
| 階層（プロジェクト / フェーズ / 工程 / マイルストン / タスク）の構造を変える | 全プリセットとガントの描画が連動している。プリセット単独では変えられない |
| 1つのドキュメントで2つのプリセットを混ぜる（プロジェクトごとに別のプリセットを使う） | 1つの HTML は1つの基準で組む。用途が2つにまたがるなら HTML を2本に分ける |
| 出力の形式やファイル名の規則をプリセット側で変える | 共通側で決まっている。用途ごとに変えると出力が探せなくなる |
| 日付の書き方をプリセット側で変える | 同上 |
| 既存のプリセットを直接書き換えて別用途にする | 元の用途で作った過去のスケジュールが、どの基準で作られたか追えなくなる。必ずコピーしてから直す |

プリセットが変えてよいのは **「何が出てくるか」と「どれくらいかかるか」** であって、
**「どう表現するか」ではない。**

---

## 呼び方を変えたいとき

「工程」「マイルストン」という言葉がその分野で馴染まない場合、
`00-preset.md` の「用語の言い換え」に、画面に出したい言葉を書く。

```markdown
| 階層 | この用途での呼び方 |
|---|---|
| 工程 | ステップ |
| マイルストン | チェックポイント |
```

**画面に出る言葉だけが変わる。** データの構造は変わらないので、他の用途のスケジュールと並べても壊れない。
