# スケジューリングの原則

日程をどう置くかの決まり。用途に依存しない部分だけをここに書く。
「どんな作業が出てくるか」「どれくらいかかるか」はプリセット側で定める。

---

## 1. 稼働日と休業日

| 項目 | 既定値 |
|---|---|
| 稼働曜日 | 月〜金 (`calendar.workingDays` = `[1,2,3,4,5]`) |
| 休業日 | 土日、および下記の休業日一覧に含まれる日 |
| 例外稼働日 | なし (`calendar.exceptionalWorkingDays` = 空) |
| 期間の数え方 | 開始日・終了日はいずれも稼働日とし、両端を含む（閉区間） |

**稼働日の定義**:

```
稼働日 = ( workingDays に含まれる曜日 かつ holidays に含まれない日 )
         ∪ exceptionalWorkingDays に含まれる日
```

タスクの開始日と終了日は、必ず稼働日に着地させる。
稼働日でない日になった場合、**開始日は直後の稼働日へ、終了日は直前の稼働日へ**寄せる。

**稼働日の定義はドキュメント全体で1つ。** プロジェクトごとに別の稼働日を持たせることはできない。
プロジェクトごとに暦が違う場合は、ドキュメントを分ける。

### 例外稼働日 (`exceptionalWorkingDays`)

**「土曜だが、この日はやる」を1日単位で書く欄。** 書いた日はその計画で稼働日として扱われ、
**所要日数 (`durationDays`) にも数えられる。**

| 項目 | 決まり |
|---|---|
| `holidays` との関係 | **逆向き。** `holidays` は稼働曜日を休みにし、こちらは非稼働日を稼働にする |
| 優先 | **`holidays` より強い。** 両方に同じ日があれば稼働日として扱う |
| 既定 | **空。** 何も書かなければ、この項目が無かった頃と挙動は1つも変わらない |

**生成時は、依頼文に根拠があるときだけ書く。**

| 場面 | どうするか |
|---|---|
| 依頼文に休日の作業日が明示されている（「イベント本番は 11/22（日）」「12/6（土）に検収立ち会い」） | **その日を `exceptionalWorkingDays` に入れ、そこに日程を置く。** 理由を `meta.assumptions` に1件残す |
| 依頼文に根拠が無い | **入れない。** 日程は平日にだけ置く |
| **目標日に間に合わない** | **入れない。** 詰め方は第3章 Step 5 の「並行化 → 増員 → 超過」で固定。**休日出勤で辻褄を合わせない** |

**間に合わせるために休日を使わないのが要点。** 依頼文に書かれていない休日を機械が勝手に使うと、
**人の休みを黙って削った計画が出る。** 足りないなら足りないと出す。

**この節を消せば、生成側は休日を一切使わなくなる**（画面での編集は影響を受けない）。
生成が余計なことをする場合は、節ごと消してよい。

### 変更時の影響（例外稼働日）

- 例外稼働日を足すと、その日をまたぐタスクの所要日数が1日ずつ増える（＝終了日が前へ動く）。
- 画面で休日に日程を置くと、この一覧が自動で増える。**減りはしない**ので、
  作り直すときに使っていない日が残っていないかを見る。

**その年の分をここに追記してから日程を計算する。** 追記せずに進めると、休業日が稼働日として計算される。

### 変更時の影響

- 稼働曜日を減らすと、同じ所要日数でも終了日が後ろへ動く。全体の期間が伸びる。
- 一覧に日付を足すと、その日をまたぐタスクの終了日が1日ずつ後ろへ動く。
- 年をまたぐ案件を扱う場合は、翌年分の日付をここに追記しておく。追記を忘れると、休業日が稼働日として計算される。

## 2. 所要日数と工数

| 用語 | JSON フィールド | 画面での呼び方 | 意味 |
|---|---|---|---|
| 所要日数 | `durationDays` | **営業日** | 開始日から終了日までに含まれる稼働日数。カレンダー上の長さ |
| 工数 | `effortDays` | **概算工数（AI算出）** | 投入する人日。2名で5稼働日なら 10 人日 |

この2つは別物として扱う。**増員しても所要日数が比例して縮むわけではない。**

工数から所要日数を出す式は次のとおり。

```
有効人数 = 1 + (人数 − 1) × 0.7
所要日数 = ceil( 工数(人日) / (有効人数 × 実働係数) )
```

| 人数 | 有効人数 |
|---|---|
| 1 | 1.0 |
| 2 | 1.7 |
| 3 | 2.4 |
| 4 | 3.1 |

**2人目以降を 0.7 で数えるのは、分担・すり合わせ・引き継ぎに時間が取られるため。**
人数を倍にしても所要日数は半分にならない。1名のときは有効人数 1.0 なので、式は従来と同じ結果になる。

人数と実働係数はプリセットの `40-team.md` で定める。
**増員の効き方は3通り。** どれに当たるかはプリセットの `10-standard-tasks.md` で標準作業ごとに指定する。

| 効き方 | 使う人数 | どんな作業か |
|---|---|---|
| **効く**（既定） | 有効人数（上の式） | 1つの作業を複数人で分担する。分担とすり合わせの分だけ目減りする |
| **そのまま効く** | 人数をそのまま | **同じ作業を人数分、同時にこなせる。** 1人あたりの持ち分が独立していて、すり合わせが要らない |
| **効かない** | 掛けない（`所要日数 = ceil( 工数 / 実働係数 )`） | 複数人で分担しづらい。手順が直列 |

**「そのまま効く」は例外的な指定。** 迷ったら「効く」にする。
**増員が効かない作業は、何人足しても短くならない。** ここが期限に間に合わない案件の下限を決める（第3章 Step 5）。

**実働係数は役割に紐づく値であり、作業の種類には紐づかない。**

`effortDays` は生成時の見積もりであり、画面では読み取り専用として出す。
画面でバーを動かしても追随しない値なので、**実績として使わない。**

### 所要日数が長くなりすぎたとき

1タスクの上限は**15稼働日**（`10-hierarchy.md` 第2章）。式の結果がこれを超えたら分割する。

| 決めること | 決まり |
|---|---|
| 何を分けるか | **工数を分ける。** 所要日数を分けない（分けた後に、それぞれ式で所要日数を出し直す） |
| 分け方 | 既定は**前段4：後段6**。前段は調べる・たたき台を作る、後段は決める・仕上げる |
| 2つで足りないとき | 均等に3分割する。4分割以上が必要なら、そのタスクは1つの作業ではないので、作業の切り方から見直す |
| 並べ方 | 同じ役割が担当するので**直列**に置く（第4章の制約） |
| 名前 | 対象で区別する。標準作業名をそのまま2つ並べない |

実働係数が低い役割（0.4 など）では、標準的な工数でも上限を超えることがある。**分割は例外ではなく、通常の手順。**

### 変更時の影響

- 式そのものを変えると全プリセットの見積もりが一斉に動く。個別の用途で調整したい場合は、この式ではなくプリセットの数値を変える。
- 2人目以降の係数 0.7 を 1.0 に戻すと、増員すればいくらでも短くなる計画が出るようになる。
- 分け方（4：6）を均等（5：5）に変えると、前段の見積もりが甘くなりやすい。

## 3. いつ始めて、いつ終わるか

依頼には「いつまでに」（目標日）と「いつから」（着手時期）の2つが出てくる。**この2つは別物。**
「年内に公開したい」は目標日、「来春から取りかかる」は着手時期であり、混同すると依頼と逆の計画になる。

### Step 1. 入力文から2つの日を読み取る

まず、それぞれの言い回しを1つの日付に確定する。

| 指定のされ方 | 目標日として読むとき | 着手時期として読むとき |
|---|---|---|
| 具体的な日付 | その日 | その日 |
| 「〜までに」「〜に公開」 | 指定日そのもの。前日ではない | — |
| 「〜から」「〜に着手」「〜スタート」 | — | 指定日そのもの |
| 「11月中」のような月単位 | その月の最終営業週の金曜日 | その月の最初の稼働日 |
| 「上旬 / 中旬 / 下旬」 | 第1週 / 第3週 / 最終週の金曜日 | 第1週 / 第3週 / 最終週の最初の稼働日 |
| 「年内」 | その年の最終稼働日 | — |
| 「年明け」「来年早々」 | — | 翌年の最初の稼働日 |
| 「今期中」「年度内」 | 年度の最終稼働日（年度末は既定で3月末。`50-user-context.md` で変えられる） | — |
| 「来期」「来年度」 | 年度の最終稼働日 | 年度の最初の稼働日 |
| 「第1四半期」などの四半期 | その四半期の最終稼働日 | その四半期の最初の稼働日 |
| 「来月」 | 翌月の最終営業週の金曜日 | 翌月の最初の稼働日 |
| 「来春 / 来夏 / 来秋 / 来冬」 | 3〜5月 / 6〜8月 / 9〜11月 / 12〜2月 の最終稼働日 | 同じ期間の最初の稼働日 |
| 「なるべく早く」「急ぎ」 | 目標日なしとして扱う | 「今日」の翌稼働日 |

**確定した日付と、その根拠を `meta.assumptions` に必ず記録する。**
「年内公開」を 12/25 と読んだのか 12/28 と読んだのかで、計画全体が動くため。

### Step 2. どちらが指定されているかで積み方を決める

| 入力文にあるもの | 積み方 |
|---|---|
| 目標日だけ | 目標日から**後ろ向き**に積む（Step 3 へ） |
| 着手時期だけ | **その日を起点に前向き**に積む。終了日は積んだ結果になる |
| 両方 | **着手時期を起点に前向き**に積み、終わりを目標日と突き合わせる（Step 4 へ） |
| どちらも無い | **「今日」の翌稼働日**を起点に前向きに積む |

**着手時期が「今日」より前の日を指している場合**は、「今日」の翌稼働日を起点にし、
そのことを `meta.assumptions` に書く。過去から始まる計画を出さない。

### Step 3. 目標日から後ろ向きに積む（目標日だけがあるとき）

最後の工程から順に、必要な稼働日数を差し引いていく。
工程の並びはプリセットの `20-structure.md` に従う。各工程の中は、後ろのタスクから順に置いていく。

### Step 4. 目標日に間に合うかを評価する

| 結果 | 対応 |
|---|---|
| 目標日に間に合う（後ろ向きに積んだ着手日が「今日」以降 / 前向きに積んだ終了日が目標日以前） | そのまま採用する。**余った期間をバッファに上乗せしない。** 後ろ向きに積んだ場合は、着手日を実際の開始予定に寄せる |
| 目標日を超える | 期間が足りていない。**Step 5 で詰める** |

### Step 5. 足りない分を詰める

**目標日に間に合う計画を出す。** 超過したままの計画を最初の答えとして出さない。
ただし**間に合わせるために何が必要かを、必ず前提とリスクに書く。**
計画の上では間に合っていても、いまの体制のままでは間に合わないことを、読んだ人が分かる状態にする。

次の順に適用し、**目標日に届いた時点で止める。** 上の手ほど副作用が小さい。

| 順 | 手 | やること | 上限 |
|---|---|---|---|
| 1 | **並行化** | プリセットの `30-estimation.md` 第5章で並行してよいとされている組み合わせのうち、まだ直列に置いているものを並行にする。ずらし幅（既定は先行タスクの 50%）を**最大 80%** まで詰めてよい | 同時に走らせられる作業本数の上限（`40-team.md`）を超えない。**同じ役割のタスクを重ねない**（第4章） |
| 2 | **増員** | 増員が効く標準作業を担う役割の人数を増やし、**所要日数を計算し直す**（第2章）。**同一役割のタスクを重ねるためには使わない**（第4章。検証 C10 は人数を見ない） | **1役割あたり、既定の人数の3倍まで、かつ5名まで**（`50-user-context.md` 第2章で変えられる）。同時に走らせられる作業本数の上限は既定の2倍まで |
| 3 | **超過を出す** | 1と2で届かない場合。**着手日を「今日」の翌稼働日に固定し、目標日を超えたまま出す** | — |

**増員で短くならない作業がある。** 「増員が効かない」とされた標準作業（第2章）と、
自分たちで縮められない待ち時間（プリセットの `50-domain-notes.md` 第1章）は、何人足しても1日も縮まない。
**この2つが直列に並んだ長さが、その計画の下限になる。** 下限が目標日を超えていれば、Step 5 の3へ進む。

**どの手を使っても、バッファを削って辻褄を合わせない。**
バッファは遅れを吸収するために置いてあり、計画上の数字を合わせるために消すものではない。

### 記録すること

| 使った手 | `meta.assumptions` に書くこと | `risks` に書くこと |
|---|---|---|
| 並行化 | どのタスクとどのタスクを並行にしたか | 先行が遅れたときに手戻りする範囲 |
| 増員 | **どの役割を何名にしたか。既定は何名か。** 目標日に間に合わせるための増員であること | **その人数を確保できない場合、目標日に何稼働日届かないか** |
| 超過を出した | 目標日をそのまま書き、計画上の終了日との差を書く | **期日に対して何稼働日不足しているか。** 縮まらない作業がどれか。範囲を削る選択肢 |

**増員を前提にした計画は、報告でも必ず口に出す。** データに書いてあっても、
読んだ人が既定の体制で間に合うと受け取ると、この記録は役に立たない。

### 複数プロジェクトの場合

**プロジェクトごとに独立して積む。** プロジェクト間で日程を調整しない
（体制の取り合いは第4章の制約の範囲外であり、第9章のリスクとして残す）。
増員も、プロジェクトごとに必要な数を出したうえで、**合計を報告する**。

### 変更時の影響

- 月単位の指定の解釈（最終営業週の金曜）を変えると、月指定のすべての案件で目標日が動く。
- Step 5 を「超過をそのまま出す」だけに戻すと、依頼された日に間に合う案が誰からも出てこなくなる。
- Step 5 の上限（1役割3名）を外すと、人を並べれば何でも間に合う計画が出るようになる。実行できない計画は、無い計画と同じ。
- Step 5 に「バッファを削る」を足すと、期日は守れる計画が出るようになるが、無理のある計画を検知できなくなる。

## 4. 並行と直列

### 表し方

| 関係 | 依存の型 | 使いどころ |
|---|---|---|
| 前が終わってから始める | `FS` | 既定。前段の成果物がないと着手できない |
| 前と同時に始める | `SS` + `lagDays` | 前段が途中まで進めば着手できる |
| 前と同時に終える | `FF` | 締め切りを揃えたい |
| 前が始まってから終える | `SF` | まれ。引き継ぎのある交代作業 |

並行の既定のずらし幅は、**先行タスクの所要日数の 50%**（`SS` + その稼働日数の `lagDays`）とする。

### 制約

- 同時に走らせられる作業本数の上限を超えない。上限はプリセットの `40-team.md` で定める。
- **同じ役割のタスクは期間を重ねない。** 重ねる必要がある場合は、**直列に並べ直す。**
  **人数を増やしても重ねない。** 増員は所要日数を縮める側にだけ効く（第2章）。
  **検証（C10）は人数を見ずに一律で重なりを弾くので、増やしたことを理由に重ねると検証が通らない。**
  この制約は、ガント上で1人の負荷の山が見えるようにするためのもの。
  **判定は1つのプロジェクトの中で行う。プロジェクトをまたいだ重なりは見ない。**
  体制（`resources`）はドキュメントに1つしか無く、別チームでも同じ役割名を使うことになるため。
  プロジェクトをまたいで同じ人が動く場合は、その取り合いを `risks` に1件書く。
- どの標準作業どうしを並行してよいかは、プリセットの `30-estimation.md` で定める。

### 変更時の影響

- ずらし幅の既定値 50% を小さくすると着手が早まり期間が縮むが、先行タスクの手戻りを受ける確率が上がる。
- 「同じ役割のタスクを重ねない」を外すと、1人が同時に3本抱える計画が平然と出るようになる。
- 判定範囲をプロジェクトをまたぐ形に広げると、別チームの作業が重なっているだけで警告が出続ける。

## 5. バッファの置き方

**バッファは独立したタスクとして置く。個々のタスクに埋め込まない。**
埋め込むと、消費されたことに気づけなくなるため。

| 項目 | 決まり |
|---|---|
| 表現 | タスクに `isBuffer: true` を立てる。**これだけ** |
| 工数 | 常に `effortDays: 0`（画面では「—」と出る） |
| 担当 | `assigneeRole` を付けない |
| 状態 | 他のタスクと同じく `status` を書く。**予備日も消化されれば「完了」にする**（そうしないと配下が完了しきらず、親に取り消し線が付かない） |
| 置き場所 | 節目の直前。そのマイルストンの最後のタスクとして置く。工程を挟まない形でも同じ（マイルストンの末尾に置く） |
| 量 | プリセットの `30-estimation.md` で定める |

期日が固定されていてバッファが確保できない場合は、
**バッファを削るのではなく** `risks` に「バッファ不足」を明記したうえで、範囲を削る選択肢を提示する。

### 改版のときに量を計算し直すか

バッファの量は比率で決まることが多い（「実装工程の 10%」など）。改版で工程の長さが変わったとき、
**この比率を自動では計算し直さない。**

| 場面 | どうするか |
|---|---|
| 日程だけを動かした（後ろ倒し、待ちが入った、遅れが出た） | **計算し直さない。** 既に置いた予備日をそのまま残す |
| 作業を足した・減らした（やることの範囲が変わった） | **その工程のバッファだけ計算し直す。** 差分を予備日の日数に反映し、`changeLog` に1行残す |
| 予備日が消費された（`done` になった、日数を削った） | **減った状態を正とする。** 自動で戻さない |

**予備日は残高として扱う。** 改版のたびに満額に戻すと、何日食ったのかが分からなくなる。

### 変更時の影響

- バッファをタスクに埋め込む方針に変えると、ガント上でバッファ行が消え、遅延の吸収余地が見えなくなる。
- 置き場所を「工程の末尾」から「各タスクの後ろ」に変えると、行数が大幅に増える。

## 6. クリティカルパス

依存関係をたどって、遅れがそのまま最終日に波及する経路をプロジェクトごとに1本特定し、
その経路上のタスクに `isCriticalPath: true` を立てる。

バッファもこの経路に含める。バッファが経路上にあることで、「ここを使い切ると期日が動く」がデータとして残る。

**Phase 1 では画面に描かない。** データとしてだけ持つ。

## 7. タイムラインの範囲と初期表示

| 項目 | 決め方 |
|---|---|
| `timelineStart` | 全プロジェクトの全タスクの最早開始日を含む週の、最初の稼働日 |
| `timelineEnd` | 「全プロジェクトの全タスクの最遅終了日 + 3稼働日」を含む週の、最後の稼働日 |
| `today` | 生成日 |

`timelineStart` / `timelineEnd` は**ドキュメント全体の範囲**を表す。
ただし**画面の横軸はこの範囲をそのまま使わず、表示中フェーズの期間を月境界に丸めた範囲に絞る**（仕様書 2-7）。
全体の範囲は、フェーズが期間を持たない場合のフォールバックと、タスクが範囲内にあることの確認に使う。

**`today` は「開いた日」を表す。** 生成時は生成日を書くが、その後に手で更新されうる値であり、
`meta.generatedAt` と一致していなくてよい。改版時は現在日に更新する。

**`today` がタイムラインの範囲の外にあってよい。** 着手が数か月先の計画では自然に起きる状態であり、
範囲に収めるために `timelineStart` を今日まで伸ばさない（伸ばすと、何も無い期間が横軸に何か月分も出る）。
範囲の外にある場合、画面に「今日」の線は出ない。**その状態で出したことを報告に1行添える。**

初期表示の設定は `display` に置く。

| 項目 | 決め方 |
|---|---|
| `display.defaultZoom` | 表示するフェーズの期間が6週間以下なら `day`、6週間超〜6か月なら `week`、6か月超なら `month` |
| `display.defaultProjectId` | **依頼の主題にあたるプロジェクトの id。判断が付かなければ省略する**（下記） |
| `display.defaultPhaseId` | **依頼の主題にあたるフェーズの id。判断が付かなければ省略する**（下記） |
| `display.defaultExpandLevel` | **常に `auto`。** 入力文で開き方が明示的に指定された場合にだけ、`milestone` / `task` のどちらかを使う |

#### `display.defaultProjectId` と `display.defaultPhaseId`（最初に開くもの）

画面は一度に1つのプロジェクトの1つのフェーズだけを表示する。その最初の1組を指定する項目。

| 状況 | どうするか |
|---|---|
| 依頼の主題がはっきり1つのフェーズに乗っている | **`defaultPhaseId` にそのフェーズの id を書く。** `defaultProjectId` は書かなくてよい（フェーズから親プロジェクトが決まる） |
| 主題はプロジェクトまでは決まるが、どのフェーズかは決まらない | `defaultProjectId` だけを書く |
| 主題がプロジェクトやフェーズをまたぐ | **どちらも省略する** |
| 判断が付かない | **どちらも省略する** |
| プロジェクトもフェーズも1つしかない | 省略してよい（結果は同じ） |

**迷ったら書かない。** 省略すると、HTML を開いた日を基準に自動で選ばれる。
書いて外すより、自動選択に任せるほうが害が小さい。

**両方書く場合は、同じプロジェクトを指していること。** 食い違うと `defaultPhaseId` のほうが優先され、警告が1件出る。
`defaultProjectId` だけを書き換えて `defaultPhaseId` を直し忘れる、という落とし方をしやすい。

書いた場合は、**なぜそれにしたかを `meta.assumptions` に1行残す。**

**書いた後に構成を組み直したら、指定が生きているかを必ず確認する。**
存在しないものを指したままでも HTML は開くが、意図と違うものが出る（仕様書の不変条件 C15 / C16）。

#### `display.defaultExpandLevel`

**値は `auto` / `milestone` / `task` の3つ。**

| 値 | 見えている状態 |
|---|---|
| `auto` | `milestone` の状態を基点に、今日が期間に入っているマイルストンだけタスクまで開く（既定） |
| `milestone` | 工程（あれば）とマイルストンだけ。画面の「タスクを畳む」と同じ状態 |
| `task` | 表示中フェーズのすべて。画面の「タスクまで開く」と同じ状態 |

**どの値でも、マイルストンは必ずすべて見えている。**
「マイルストンが1つも見えない状態を作らない」という原則があるため。

**判定は表示中のフェーズの内側で完結する。** 他のフェーズも、他のプロジェクトも見に行かない。

表示中のフェーズに今日が入っていない場合は、そのフェーズの中で「これから最初に始まるマイルストン」が1件だけ開く。
**今日が別のフェーズや別のプロジェクトにあるのは珍しい状況ではない**ので、この経路は普通に通る。

`auto` の判定手順とフォールバックの規定は、仕様書の「ガント描画へのマッピング」にある。

### 変更時の影響

- 範囲を広げるとガントの横幅が伸び、日単位表示では横スクロール量が増える。
- `defaultZoom` / `defaultProjectId` / `defaultPhaseId` / `defaultExpandLevel` を変えると、HTML を開いた直後の見え方だけが変わる。データそのものは変わらない。
- `auto` 以外の固定値を既定にすると、開いた直後に「いま進んでいるところ」が見えなくなり、毎回スクロールと開閉の操作が要る。
- `defaultPhaseId` を常に書く運用にすると、時間が経ってから開いたときに、とっくに終わったフェーズが最初に出ることになる。
  自動選択は開いた日を見るので、この問題が起きない。**省略を既定の選択肢として扱う。**

## 8. 状態の書き方

状態 (`status`) は `notstarted`（未着手）/ `inprogress`（進行中）/ `done`（完了）の3値。

| 階層 | 書くか | 理由 |
|---|---|---|
| **タスク** | **必ず書く（必須）** | 状態を人が入れる唯一の階層。画面から切り替えられるのもここだけ |
| プロジェクト・フェーズ・工程・マイルストン | **書かない** | 常に配下から算出する（`10-hierarchy.md` 第4章）。書いても使われない |

初版の生成では、**全タスクを `notstarted` にする。** 入力文で「設計は済んでいる」のように
既に終わった作業が示されている場合だけ、該当タスクを `done` にし、その判断を `meta.assumptions` に残す。

改版で進捗が伝えられた場合は、該当タスクの `status` を更新する。
`done` にしたタスクは `progress` を 100 にする。

**停滞（ブロック）を表す値は持たない。** 進んでいないことは日付から読める。
止まっている理由を残したい場合は `risks` に1件書くか、タスクの `notes` に書く。

### 変更時の影響

- 親の階層にも状態を書く運用に戻すと、タスクを1件完了にしても親の見た目が変わらない状態が生まれ、取り消し線が信用できなくなる。
- 停滞を表す4つ目の値を足すと、画面で3段階の濃さに乗らない値が1つ増え、記号か色を足すことになる。

## 9. リスクの記録

次に当てはまる場合は、`risks[]` に必ず1件記録する。

| 状況 | 記録する内容 |
|---|---|
| 期日が固定で、バッファがプリセットの基準量に満たない | 吸収できる余地が何日しかないか |
| 前例のない作業を含む（プリセットの条件倍率を適用したタスクがある） | どのタスクが該当し、何が読めないか |
| 自分たちの外側の要因で待ちが発生する | 誰の何を待っているか |
| 並行させたことで手戻りの範囲が広がっている | どのタスクとどのタスクが連動するか |
| **複数のプロジェクトが同じ体制を共有している** | どのプロジェクトとどのプロジェクトが、どの役割を取り合うか |
| **目標日に間に合わせるために体制を増やした**（第3章 Step 5 の2） | どの役割を何名にしたか。**その人数を確保できない場合、目標日に何稼働日届かないか** |
| **増員と並行化でも目標日に届かなかった**（第3章 Step 5 の3） | **何稼働日不足しているか。** 縮まらない作業がどれか。範囲を削る選択肢 |

各リスクには `mitigation`（顕在化した場合の対処方針）を必ず書く。書けないリスクは、リスクではなく前提として `meta.assumptions` に置く。

### 変更時の影響

- 記録の条件を緩めると `risks[]` が空になりやすくなり、無理のある計画がそのまま通る。
- 最後の1行を外すと、複数プロジェクトを1本に束ねたときに、体制の取り合いがどこにも残らなくなる（同一役割の重なりの判定はプロジェクト内で完結するため、警告としては出ない）。
