# この用途ならではの注意点

## 1. 自分たちで縮められない期間

| 何を待つか | 目安の期間 | 短縮できるか |
|---|---|---|
| 配信ストアの審査 | 3〜10稼働日 | できない。申請日を前倒しするしかない |
| 外部サービスの利用申請・本番権限の付与 | 3〜10稼働日 | できない。着手と同時に申請しておく |
| 取引先や他部署の環境側の設定変更 | 5稼働日以上 | できない。依頼のタイミングを早める |

これらは「外部要因の待ち」の独立したタスクとして置き、`assigneeRole` を付けない。**予備日ではないので `isBuffer` は立てない。**
実装の裏で並行させ、公開日から逆算して申請日を決める。

## 2. 後ろ倒しができない日

| 何 | なぜ動かせないか |
|---|---|
| 外部に告知済みの公開日 | 利用者への案内が先行している |
| 契約や制度の切り替え日に合わせた公開 | 制度側の日付が固定されている |
| 大型連休の直前・直後を避ける必要がある公開 | 障害時に対応できる人がいない |

こうした日がある場合、その直前に必ず公開バッファを置く。
**連休の直前の公開は避け、連休明けの稼働日に置く。** 直前に置くと、障害が出たときに数日放置される。

## 3. 見落としやすい作業

- 既存機能への影響確認（回帰テスト）。新機能のテストだけを積んで漏らしやすい
- 本番のデータ移行と、その切り戻し手順の用意
- 監視の設定追加。公開してから「見えていない」ことに気づく
- 利用者向けの案内文・ヘルプの更新
- 権限設定と、公開範囲の確認

これらを工程テンプレートが拾えていない場合、該当する標準作業のタスクとして足す。

## 4. この用途で必ず記録するリスク

共通側（`definitions/20-scheduling-rules.md` 第9章）の条件に加えて、次を記録する。

| 状況 | 記録する内容 |
|---|---|
| 新規の技術要素に倍率 1.3 を適用したタスクがある | どのタスクが該当し、方式が成立しなかった場合の代替が何か |
| サーバ側と画面側を並行させている | 設計変更が起きたときに、どこまで手戻りするか |
| 検証の担当が実装の担当と同じ | 作った本人が検証することで見落とす範囲 |
| 公開日が固定で、バッファが基準量に満たない | 吸収できる余地が何日しかないか |

---

## 変更時の影響

- 第1章に行を足すと、その待ち時間が独立したタスクとして計画に現れ、全体の期間が伸びる。実態に合っていれば、伸びるのが正しい。
- 第3章の項目は工程テンプレートに昇格させることもできる。頻繁に足しているものがあれば `20-structure.md` に移す。
