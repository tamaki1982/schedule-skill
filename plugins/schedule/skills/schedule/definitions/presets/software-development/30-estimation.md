# かかる日数の基準

標準作業ごとの標準工数と、それに掛ける倍率。「標準」規模の案件を基準にしている。
標準作業の一覧は `10-standard-tasks.md` にある。

## 1. 標準作業ごとの標準工数

| 標準作業 | 標準工数 | 上限側を採る条件 |
|---|---|---|
| 要件定義 | 6〜8人日 | 既存機能への影響範囲が広い場合。調査と仕様確定の2本に分ける |
| 画面設計 | 5〜8人日 | 主要画面が4つ以上ある場合 |
| 技術設計 | 5〜7人日 | 新規の通信方式やデータ基盤を含む場合 |
| 基盤・環境構築 | 3〜5人日 | 既存基盤の流用ができない場合 |
| サーバ側実装 | 7〜10人日 | 外部サービスとの連携を含む場合。1つの実装単位あたり |
| 画面側実装 | 8〜13人日 | 状態管理が複雑な画面を含む場合。画面1〜2つの実装単位あたり |
| 結合 | 6〜9人日 | つなぐ相手が2系統以上ある場合。想定外の調整が入りやすいため多めに置く |
| 動作テスト | 5人日 | 結合テストと受け入れテストでそれぞれ1本 |
| レビュー | 1〜2人日 | 確認する相手が3名以上いる場合 |
| 公開作業 | 1〜3人日 | 切り戻し手順の検証を含む場合。準備と反映を分けてよい |
| 外部要因の待ち | 0人日 | 縮められない待ち時間として置く（`50-domain-notes.md` 第1章）。期間は個別に判断 |
| （予備日） | 0人日 | 標準作業ではない。量と位置は第4章 |

**書いてあるのは工数（人日）だけ。所要日数（カレンダー上の長さ）はここに書かない。**
所要日数は `40-team.md` の人数と実働係数から式で出す（`definitions/20-scheduling-rules.md` 第2章）。
両方を持つと必ずどちらかが式と合わなくなるため、工数だけを正とする。

```
有効人数 = 1 + (人数 − 1) × 0.7
所要日数 = ceil( 工数(人日) / (有効人数 × 実働係数) )
```

**既定の体制（各役割1名）では、所要日数は工数より長くなる。**
たとえば要件定義 6人日をプロダクト管理（1名 / 実働係数 0.4）が担当すると 15稼働日になる。
これは上限（15稼働日）に達しているので、**上の表のとおり調査と仕様確定の2本に分ける**（分け方は共通側 第2章）。

### 変更時の影響

- 標準工数を増やすと、その作業を含むすべてのスケジュールの期間が伸びる。
  公開日が固定されている案件では、増員を前提にした計画になるか、機能範囲を削るリスク記述が増える。
- 実働係数の低い役割が担当する作業では、工数を1〜2人日増やしただけでタスクが2本に分かれる。

## 2. 規模による倍率

| 規模 | 倍率 |
|---|---|
| 小さい | 0.5 |
| 標準 | 1.0 |
| 大きい | 1.5〜2.0 |

**倍率は工数に掛ける。** 所要日数には掛けない（第3章と同じ）。

## 3. 条件による倍率

**該当タスクの工数（`effortDays`）に掛ける。所要日数には掛けない。** 複数該当する場合は掛け合わせる。

| 条件 | 倍率 |
|---|---|
| 新規の技術要素を含む（使ったことのない方式・外部サービス） | 1.3 |
| 外部サービスとの連携がある | 1.2 |
| 既存機能への影響範囲が広い（既存画面の改修を伴う） | 1.2 |
| 仕様が固まっていない状態で着手する | 1.3 |

```
工数 = 標準工数 × 規模倍率 × 条件倍率（掛け合わせ）
所要日数 = ceil( 工数 / (有効人数 × 実働係数) )   ← 端数の切り上げは最後に1回だけ
```

倍率を適用したタスクがある場合、そのことを `task.notes` に書き、`risks[]` にも1件記録する。

### 変更時の影響

- 倍率を上げると、その条件に当てはまる案件だけ期間が伸びる。
  特定の種類の案件で見積もりが甘いと感じたときは、標準工数ではなくこちらを調整するほうが副作用が小さい。
- 掛け先を所要日数に変えると、切り上げが2回入って結果が変わる。掛け先は工数で統一する。

## 4. バッファの量

| 種類 | 量 | 置き場所 |
|---|---|---|
| 実装バッファ | 実装工程の経過稼働日数の 10%、最低2稼働日 | 実装工程の末尾、機能実装完了マイルストンの直前 |
| 公開バッファ | 1稼働日以上 | 本番公開マイルストンの直前 |
| 検証バッファ | 検証工程の経過稼働日数の 10%（任意） | 受け入れテスト完了マイルストンの直前 |

置き方の原則（独立したタスクとして置く、`isBuffer: true`、工数 0、担当を付けない）と、
改版のときに量を計算し直すかは `definitions/20-scheduling-rules.md` 第5章で共通に決まっている。

### 変更時の影響

- 比率を上げると全体の期間が伸びる。公開日が固定の案件では、その分だけ着手日が前倒しになる。

## 5. 並行してよい組み合わせ

**この章のすべての行に、次の2つが先に効く。**

| 先に効く決まり | 内容 |
|---|---|
| **同じ役割のタスクは重ねない** | 並行してよい組み合わせであっても、**担当が同じ役割なら直列に置く**（`40-team.md` 第2章）。**人数を増やしても重ねられない** |
| 同時本数の上限 | 同時に走らせられる作業本数（既定3）を超えない（`40-team.md` 第2章） |

そのうえで、並行してよい組み合わせは次のとおり。

| 先に進むもの | 並行して進めてよいもの | 着手のタイミング |
|---|---|---|
| 要件定義 | 画面設計・技術設計の両方 | 要件定義が半分進んだ時点 |
| 画面設計 | 画面側実装 | 画面設計の確定分から。全体の確定を待たない |
| サーバ側実装 | 画面側実装 | 画面設計とデータ構造が確定していれば同時に進めてよい |
| 動作テスト | 指摘対応（サーバ側実装 / 画面側実装） | テスト開始から2稼働日後 |
| サーバ側実装 | 基盤・環境構築 | データ構造が確定した時点 |

並行は `SS` + `lagDays` で表す。既定のずらし幅は先行タスクの所要日数の 50%
（目標日に間に合わせるために詰める場合は最大 80%。共通側 第3章 Step 5）。

**並べたあとに前後が逆転していないか確認する。**
後のタスクの開始日を先行タスクの開始日より前に置かない。終了日も先行タスクの開始日より後にする。

## 6. 直列にすべき組み合わせ

| 順序 | 理由 |
|---|---|
| 要件定義 → 設計（画面・技術） | 要件が動くと設計をやり直すことになる |
| データ構造の実装 → それを使う実装 | 先に型を固めないと両方が手戻りする |
| 実装 → 結合 → 動作テスト | 前段が終わらないと意味のある作業にならない |
| 動作テスト → 公開作業 | 例外を作らない |

### 変更時の影響

- 並行してよい組み合わせを増やすと期間は短くなるが、同時進行の本数が `40-team.md` の上限を超えると実行不可能な計画になる。上限とセットで見直す。
- 「実装 → 結合 → テスト」の直列を崩すと、テスト工程で手戻りが多発する計画になる。

## 7. 同じ作業が繰り返し出るとき

1つのフェーズの中に同じ標準作業が2回以上出ることがある。
機能A・機能B・機能Cそれぞれに要件定義を置く場合や、実装を前半・後半に割った場合が該当する。
**2回目以降は1回目より軽くなる。** 進め方が決まっていて、判断の材料も揃っているため。

| 何回目か | 工数に掛ける係数 |
|---|---|
| 1回目 | 1.0 |
| 2回目 | 0.7 |
| 3回目以降 | 0.5 |

| 決めること | 決まり |
|---|---|
| 下限 | 0.5人日を下回らない |
| 数える範囲 | **同じフェーズの中**。フェーズが変われば1回目に戻す |
| 同じにならない場合 | 対象の大きさが機能ごとに大きく違うなら、係数を使わず個別に見積もる |
| 適用しない作業 | 動作テスト・公開作業（回数を重ねても手順を通す時間は減らない） |
| 記録 | 係数を適用したことを `meta.assumptions` に1行残す |

### 変更時の影響

- 係数を 1.0 に戻すと、機能を複数並べる案件で期間が目に見えて伸びる。
- 下限を外すと、4つ目以降の機能の要件定義が 0 に近づき、実際には必ずかかる時間が計画から消える。
