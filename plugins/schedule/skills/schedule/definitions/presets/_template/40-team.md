# 体制と稼働

> 入力文で体制の指定がない場合に採用する前提を書く。
> **実働係数が日程に一番効く。** ここを埋めれば、他が多少雑でも実用的な日程が出る。
> 記入したら、この引用ブロックは削除する。

## 1. 既定の体制

| 役割 id | 表示名 | 人数 | 実働係数 |
|---|---|---|---|
| | | 1 | |
| | | 1 | |

実働係数は、1稼働日のうちその案件に使える割合。

| 状況 | 目安 |
|---|---|
| 専任 | 0.8（会議や問い合わせで2割は消える前提） |
| 他の仕事と半々 | 0.4〜0.5 |
| 片手間 | 0.2〜0.3 |

所要日数は次式で算出する（式は共通側で決まっている）。

```
有効人数 = 1 + (人数 − 1) × 0.7
所要日数 = ceil( 工数(人日) / (有効人数 × 実働係数) )
```

2人目以降を 0.7 で数えるのは、分担とすり合わせに時間が取られるため。既定の1名では有効人数 1.0 になる。

`10-standard-tasks.md` 第1章で「増員が効かない」と指定した標準作業には、人数を掛けない。

**実働係数は役割に紐づく値であり、作業の種類には紐づかない。**

目標日に間に合わせるために人数を増やす場合の上限は、`definitions/20-scheduling-rules.md` 第3章 Step 5 と
`definitions/50-user-context.md` 第2章にある（既定は、既定の人数の3倍まで、かつ5名まで）。

### 変更時の影響

- 人数を増やすと、同じ工数でも所要日数が短くなり、全体の期間が縮む。
- 実働係数を下げると全タスクの所要日数が伸びる。
  見積もりが常に楽観的すぎると感じたときは、標準日数ではなくここを下げるほうが影響が読みやすい。
- 役割を追加したら、`10-standard-tasks.md` の「既定の担当役割」からも参照できるようにする。

## 2. 同時並行の上限

| 項目 | 既定値 |
|---|---|
| 同時に走らせられる作業本数 | 3 |
| 1役割が同時に持てる作業本数 | 1 |

同じ役割のタスクを期間を重ねて配置しない。重ねる必要がある場合は、**直列に並べ直す。**
**人数を増やしても重ねない。** 増員は所要日数を縮める側にだけ効く（`definitions/20-scheduling-rules.md` 第2章 / 第4章）。

### 変更時の影響

- 上限を上げると期間は縮むが、実際の体制で回せない計画になりやすい。人数とセットで見直す。
- 「1役割が同時に持てる作業本数」を 2 以上にすると、同一担当のタスクが重なって配置され、ガント上で負荷の山が見えなくなる。

## 3. その他の稼働の前提

| 項目 | 既定値 | 備考 |
|---|---|---|
| 割り込み対応 | 実働係数に内包 | 別枠のタスクとしては置かない |
| 確認・承認の待ち時間 | 各タスクに +0稼働日 | 待ちが長い用途では独立したタスクとして置く |
| 自分たちの外側の要因による待ち | 個別に記載 | `50-domain-notes.md` に該当があれば、独立したタスクとして明示する |

### 変更時の影響

- 待ち時間を +1稼働日などに変えると、タスク数に比例して期間が伸びる。手戻りや確認が多い用途では現実に近づく。
