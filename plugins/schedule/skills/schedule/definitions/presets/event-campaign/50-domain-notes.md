# この用途ならではの注意点

## 1. 自分たちで縮められない期間

| 何を待つか | 目安の期間 | 短縮できるか |
|---|---|---|
| 会場の空き確認と仮押さえ | 5〜10稼働日 | できない。企画と並行して先に押さえる |
| 出演者・登壇者の日程調整 | 5〜15稼働日 | できない。企画確定と同時に打診する |
| 社外への告知内容の確認 | 3〜5稼働日 | できない。「確認・承認」 として独立させる |

## 2. 後ろ倒しができない日

| 何 | なぜ動かせないか |
|---|---|
| 開催日 | 告知した時点で参加者の予定が押さえられている |
| 申込締切 | 参加者への案内に記載済み |
| 会場・配信環境の予約日 | 早い者勝ちで、取り直しがきかない |

**開催日が固定であることが、この用途の最大の制約。**
期間が足りない場合、後ろへ延ばすことはできない。内容の範囲を削るか、着手を前倒しするしかない。

## 3. 見落としやすい作業

- 参加者への前日リマインド
- 当日のトラブル対応の役割分担を決めておくこと
- 申込フォームの動作確認（告知した後に壊れていることに気づく）
- 開催後のお礼の連絡と、資料の共有
- キャンセル・欠席への対応

## 4. この用途で必ず記録するリスク

| 状況 | 記録する内容 |
|---|---|
| 告知開始から開催まで3週間を切っている | 申込数が定員に届かない可能性と、追加告知の余地 |
| リハーサルが開催の前日になっている | 問題が見つかっても直す時間がない |
| 会場や配信環境の確保が未確定のまま告知する | 確保できなかった場合の代替 |

---

## 変更時の影響

- 第1章に行を足すと、その待ち時間が独立したタスクとして計画に現れ、着手日が前倒しになる。
